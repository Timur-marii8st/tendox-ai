# CLAUDE.md — конвенции разработки

Инструкции для ИИ-агентов и людей, работающих над кодом этого репозитория.
Реестр *продуктовых* ИИ-агентов — в [docs/product/14-product-agents.md](docs/product/14-product-agents.md).

## Что это за проект

`Syurai Procurement` включает направление ИИ для поставщиков и планируемое
направление ИИ для заказчиков. Подробное ТЗ и текущая бета относятся к
поставщикам; границы второго направления — в [описании](docs/product/18-customer-direction.md).

Направление поставщика — мультитенантный виртуальный тендерный отдел: мониторинг
процедур → разбор документов → hard gates → поставщики/RFQ/КП → три сценария
экономики → рекомендация → подготовка и подтверждённое исполнение → post-award.

Перед задачей читать только релевантные источники: сначала [AGENTS.md](AGENTS.md)
и этот файл, затем нужный раздел [docs/README.md](docs/README.md) и связанные с
задачей документы. Полный набор документов читать не требуется; для доменной
логики обычно нужны [docs/architecture/01-domain-model.md](docs/architecture/01-domain-model.md),
[docs/architecture/03-compliance-engine.md](docs/architecture/03-compliance-engine.md),
[docs/architecture/04-economics.md](docs/architecture/04-economics.md) или
[docs/product/11-product-requirements.md](docs/product/11-product-requirements.md) — по области
изменения.

## Стек

| Слой | Технология | Почему |
|---|---|---|
| Ядро домена | Python 3.11+, pydantic v2 | Экосистема парсинга документов и LLM-тулинга |
| API | FastAPI + uvicorn | Async, OpenAPI из коробки |
| Хранилище | PostgreSQL 16 + pgvector | Реляционный домен + семантический поиск в одной БД |
| Очереди | Celery/ARQ (решение отложено, см. ADR) | Долгие задачи парсинга и RFQ |
| Пакеты | `uv` | Быстрый lockfile, воспроизводимость |
| Качество | pytest, ruff, mypy (strict на `domain/`) | Домен — критичный код |
| Frontend | Next.js (внутренний интерфейс в `web/`) | Корпоративный web-инструмент, не Telegram Mini App |

## Команды

```bash
uv sync --extra dev          # установка зависимостей
uv run pytest -q             # тесты
uv run pytest --cov=src      # покрытие
uv run ruff check . --fix    # линтер
uv run ruff format .         # форматирование
uv run mypy src/procurement/domain   # типы в ядре домена
PYTHONPATH=src uv run python -m pytest --doctest-modules src/procurement/domain   # доктесты
```

Гейт перед коммитом: все четыре команды (`pytest`, доктесты, `ruff check`,
`mypy`) должны проходить без замечаний.

## Тесты

Тесты пишутся не на «счастливый путь», а на случаи, где система могла бы
соврать пользователю. Главная метрика — **ноль ложных PASS**, поэтому каждый
инвариант домена имеет регрессионный тест:

| Файл | Что защищает |
|---|---|
| `tests/test_compliance.py` | инварианты №2, №3, №5: UNKNOWN вместо догадки, hard gate, запрет процентов при FAIL, оба источника в выводе |
| `tests/test_units.py` | инвариант №5, в первую очередь несопоставимость календарных и суточных сроков |
| `tests/test_requirements.py` | отказ модели принимать непроверяемое требование |
| `tests/test_offers.py` | инвариант №1 и «срок действия неизвестен ≠ документ действует» |
| `tests/test_economics.py` | инвариант №6: Decimal, отдельная ставка НДС, ни один расход не теряется |
| `tests/test_company.py` | юридические/коммерческие запреты и непротиворечивые лимиты |
| `tests/test_tenders.py` | timezone-aware deadline и топология доставки |
| `tests/test_decisions.py` | рейтинг не перекрывает hard gate; без КП нет рекомендации |
| `tests/test_actions.py` | approval относится к точному неизменённому payload и имеет expiry |

Данные в тестах только синтетические, фикстуры — в `tests/conftest.py`.
Тест с именем вида `test_no_percentage_on_fail` — это фиксация продуктового
запрета, удалять его нельзя без ADR.

## Инварианты домена — нарушать нельзя

Это не стилистика, а суть продукта. Изменение любого пункта требует ADR.

1. **Нет provenance — нет факта.** Любое требование ТЗ и любой атрибут товара
   несёт `Provenance` (документ + локатор). Требование без источника невалидно.
2. **Три состояния, не два.** Соответствие требованию — `PASS | FAIL | UNKNOWN`.
   Отсутствие данных никогда не превращается в `PASS`.
3. **Hard gate убивает кандидата.** Провал хотя бы одного обязательного требования
   даёт вердикт `FAIL` целиком. Проценты соответствия при провале hard-требования
   показывать запрещено — это дезинформация («96% соответствия» с проваленной
   гарантией привело бы к отклонению заявки).
4. **LLM не решает.** LLM извлекает, нормализует, предлагает сопоставления.
   Вердикт выдаёт детерминированный движок правил на структурированных данных.
5. **Единицы измерения нормализуются на входе.** В домене хранятся канонические
   единицы; исходная строка сохраняется рядом.
6. **Деньги — только `Decimal`.** `float` в денежных расчётах запрещён.
   НДС хранится отдельно от суммы, никогда не «примерно включён».
7. **Внешний текст недоверенный.** Содержимое ТЗ, писем, веб-страниц не может
   менять политику агента, выдавать разрешения или инициировать действие.
8. **Юридически значимое действие требует человека.** Подписание КЭП, подача
   заявки, отправка КП — только после явного подтверждения оператора.
9. **Секреты не попадают в LLM.** Пароли, cookies, приватные ключи, токены —
   вне промптов, телеметрии и логов приложения.
10. **Рейтинг не является допуском.** Он сортирует кейсы только после hard gates;
    зелёный балл не исправляет `FAIL` или `UNKNOWN`.
11. **Рекомендация требует КП и сценариев.** `PARTICIPATE` невозможен без
    действующего подтверждённого КП и `base/realistic/conservative`.
12. **Deadline имеет часовой пояс.** Наивные datetime запрещены; истёкшая или
    закрытая процедура не рекомендуется.
13. **Approval связан с точным payload.** Любое изменение цены, файла, адресата
    или типа действия требует нового подтверждения.
14. **Tenant isolation сквозная.** Каждый persisted aggregate, job, object и
    audit event имеет `company_id`; межтенантный доступ тестируется негативно.

## Структура

```
src/procurement/
  domain/         # чистая логика, без I/O и без сети. mypy strict.
    units.py        нормализация единиц измерения
    provenance.py   источники фактов
    requirements.py требования ТЗ
    offers.py       товарные предложения и атрибуты
    compliance.py   движок соответствия
    company.py      профиль, география, лимиты и запреты
    tenders.py      процедура, deadline и адреса поставки
    economics.py    полная стоимость и три сценария
    decisions.py    риски, рейтинг и recommendation gates
    actions.py      exact-payload approval и audit event
    lifecycle.py    этапы исполнения контракта
    platforms.py    sourcing / shelf sales, условия допуска и snapshot правил
  api/            # FastAPI, тонкий слой над домом
tests/            # зеркалит структуру src, файлы test_<module>.py
  conftest.py       синтетические фикстуры: req / attr / line_item / candidate
docs/             # тематические контракты и индексы; history/ — dated evidence
```

`domain/` не импортирует ничего из `api/`, не делает сетевых вызовов и не читает
файлы. Это делает его полностью тестируемым и переносимым.

## Конвенции кода

- Русский язык в доменных именах не используем — код английский, комментарии и
  докстринги русские. Доменные термины оставляем как есть: `ktru`, `okpd2`, `nds`.
- Публичные функции домена имеют аннотации типов и докстринг с примером.
- Никаких «умных» абстракций на будущее. Слой добавляется, когда есть второй
  реальный потребитель.
- Тест на баг пишется до фикса.
- Поле модели с именем `property` затеняет встроенный декоратор `property`
  внутри тела класса. Поэтому `Requirement.label()` и `Attribute.display()` —
  методы, а не свойства. Это не стиль, а обход `TypeError`.
- Правила ruff `RUF001/002/003` (неоднозначные кириллические символы) отключены
  в `pyproject.toml`: документация в коде русская, правила давали ~180 ложных
  срабатываний.

## Работа с документацией

Документация — часть определения готовности. При изменении поведения домена
обновляется соответствующий файл в `docs/`. Новое архитектурное решение →
новый ADR в `docs/adr/NNNN-kebab-title.md` (шаблон: Контекст / Решение /
Последствия / Альтернативы).

Факт о рынке, площадке, законе или конкуренте попадает в
[docs/research/07-research-log.md](docs/research/07-research-log.md) со статусом:
`ПРОВЕРЕНО` (есть первичный источник) / `ТРЕБУЕТ ПРОВЕРКИ` / `ГИПОТЕЗА`.
Непроверенный факт нельзя использовать как основание архитектурного решения.

## Безопасность при разработке

- Реальные ТЗ и КП клиентов — только в `samples/private/` (в `.gitignore`).
  Для тестов используем синтетические фикстуры.
- Не добавляем интеграцию с ЭТП без проверки её регламента/договора —
  см. [docs/architecture/06-legal-security.md](docs/architecture/06-legal-security.md).
- Browser automation — fallback, а не основной протокол. Обход CAPTCHA,
  anti-bot и rate limits не реализуем.

Проверка навигации документации: `uv run python scripts/check_docs.py`.
Подробные журналы хранить в docs/history/, текущую задачу — только в коротком
[плане](docs/15-implementation-plan.md). Историческое evidence сохранять.
