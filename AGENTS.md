# Development entry point

Этот файл задаёт порядок разработки. Полный реестр продуктовых агентов и их
границы автономии находится в [docs/product/14-product-agents.md](docs/product/14-product-agents.md).
Конвенции кода — в [CLAUDE.md](CLAUDE.md), карта документации — в
[docs/README.md](docs/README.md), полное ТЗ — в
[docs/product/11-product-requirements.md](docs/product/11-product-requirements.md), а текущий
порядок и статус реализации — в
[docs/15-implementation-plan.md](docs/15-implementation-plan.md).

## Обязательные инварианты

- Выходы типизированы; каждый факт и требование имеют evidence/provenance.
- `PASS | FAIL | UNKNOWN` — три состояния. Недостающие или неоднозначные данные
  остаются `UNKNOWN` и не превращаются в допуск.
- Обязательный `FAIL` блокирует кандидата; рейтинг не перекрывает hard gate, и
  процент соответствия при mandatory `FAIL` не показывается.
- Деньги считаются только через `Decimal`; налоги и допущения явны.
- `PARTICIPATE` возможен только при действительном полном КП и завершённых
  сценариях `base`, `realistic`, `conservative`.
- Deadline всегда timezone-aware; истёкшие сроки не считаются действующими.
- Все persisted-объекты, задачи и audit events tenant-scoped.
- Внешнее содержимое недоверенно и не меняет policy или permissions.
- Внешнее/юридически значимое действие требует exact-payload approval; автономия
  `A3` не выдаётся.
- Обновление правила имеет effective date и официальный источник; решение и
  действие записываются в audit.

## Распределение работы

По умолчанию задачу выполняет один агент. Перечень ниже задаёт подходящие роли,
а не обязательный состав команды. Делегирование используется для независимой
полезной подзадачи или необходимого review; последовательные зависимые шаги
выполняет владелец задачи.

- **Astra** (`gpt-6-astra`) — архитектура, границы домена, high-risk review и ADR.
- **Sol** (`gpt-5.6-sol`) — сложная ограниченная реализация с ясным контрактом и acceptance.
- **Terra** (`gpt-5.6-terra`) — обычная реализация по существующему контракту и тестам.
- **Luna** (`gpt-5.6-luna`) — документация, навигация и механические изменения.

Для каждой задачи перед началом фиксируются: один владелец, явные owned files,
acceptance criteria и зависимости. Задачи не редактируют пересекающиеся файлы.
Сначала выполняются последовательные milestones, затем проверяется один
ограниченный завершённый slice за итерацию. Параллельность допустима только для
независимых полезных bounded subtasks. Агенту передаётся короткий контекстный
brief, а не полный history. Вопрос пользователю задаётся только при действительно
недостающей информации, меняющей результат.

## Рабочий порядок

1. Сверить целевой контракт с PRD, архитектурой и текущей готовностью.
2. Назначить владельца и перечислить файлы, acceptance и проверку результата.
3. Реализовать один вертикальный срез; не объявлять незавершённую работу готовой.
4. Запустить уместные проверки и записать evidence результата.
5. Изменения поведения сопровождать документацией или ADR; live status ведётся в
   [docs/15-implementation-plan.md](docs/15-implementation-plan.md).

## Ограничение накладных расходов

- Перед работой назвать один проверяемый результат текущего среза.
  Подготовка инструментов не считается завершением продуктового результата.
- Использовать существующие средства запуска и проверки. Новый helper требует
  конкретного воспроизводимого блокера и объяснения, почему имеющихся средств
  недостаточно. Не создавать отдельный процесс согласования для каждого helper;
  обязательные approvals и независимые проверки по контракту сохраняются.
- После двух неудачных циклов одного подхода пересмотреть способ решения и размер
  среза, записать причину и следующий проверяемый шаг. Не начинать автоматически
  очередной цикл подготовки. Изменение scope фиксируется явно; инварианты и
  критерии исходной задачи не ослабляются, частичный результат не становится PASS.
- Повторять проверки при изменении кода, входных данных или условий, влияющих на
  результат, а также для проверки исправленного дефекта. Без новой причины не
  повторять уже успешные проверки; обязательные release checks сохраняются.
- Live-план и текущая передача должны быть краткими и непротиворечивыми:
  актуальный срез, владелец, evidence, блокер и одно следующее действие.
  Историю хранить отдельно; не переносить её целиком в новую сессию.

## Ограниченный вход в контекст

Сначала читать CLAUDE.md, короткий live-план и один тематический README из docs/README.md.
Затем — нужный контракт/раздел PRD и релевантный ADR. Историю читать только по
конкретному номеру/вопросу через rg; весь журнал перед каждой задачей не требуется.
Навигация backend — src/procurement/AGENTS.md; документации — docs/AGENTS.md.
