MANDATORY_FRESH_WORK_READY, SERVER_IMPORT_BUSY и промежуточные WAITING_AFTER_YIELD.

## Конкретный порядок ускорения

1. **Доступ и честная диагностика.** Проверять достижимость интеграционного сервиса
   отдельно от listener; сохранять безопасные HTTP status/service code/network
   phase и stage timings, без SOAP/token/raw exception. Различать состояние
   процесса и intake. Общий breaker при серии транспортных отказов должен
   оставлять задания pending и пробовать восстановление с ограниченным backoff.
   Он снижает бесполезные попытки, но сам не устраняет внешний сбой.
2. **Чередование подготовки архивов.** После initial response сохранять request UID
   и next_poll_at, выполнять другую разрешённую работу, затем проверять готовность.
   Начать с bounded4pending, одного общего limiter/lease и прежнего1.25s pacing.
   Не менять source quotas. Полный archive set, tenant/SHA binding, byte limits,
   atomic intake, expiry и crash recovery должны сохраниться. Сначала safe telemetry
   и controlled benchmark; до этого выигрыш1.40x остаётся верхней расчётной оценкой.
3. **Планировщик заполнения.** Использовать свободное допустимое время между cron
   для продолжения общей очереди. Явно разделить свежие обновления и историческую
   загрузку; задать глубину истории и проверяемые сроки свежести. Условие «история
   только если вся mandatory очередь пуста» пересмотреть вместе с контрактом
   свежести, а не тайно отключать guard. Изменение долей/приоритетов требует
   отдельного source-bound среза и проверки, что свежесть не ухудшилась.

Следующий минимальный implementation slice: безопасная source-error/phase telemetry
и end-to-end availability classification; затем bounded prepared queue с benchmark.
Acceptance ускорения: больше новых canonical закупок и закрытых исторических
координат за одинаковый доступный source период; HTTP search, отсутствие дубликатов,
измеренный fresh lag, сохранённые quotas/leases/RLS и отсутствие ложных PASS.
LLM не устраняет недоступность сервиса, pacing или отсутствие дат в плане.

Ограничения evidence: первый readonly diagnostic имел3SQL syntax errors из-за
alias hour; исправленные запросы — db-throughput.json. Его поле kind эвристически
не различает формат часового ключа и не использовано: разделение44 взято из
типизированного observation.lane. Исторические ошибочные отчёты сохранены.
