# Протокол пилотной проверки полного пользовательского сценария

Статус: **предварительный машинный прогон выполнен; полный human-reviewed пилот
остаётся `UNKNOWN`**.

Документ задаёт проверку одного полного сценария на 10–20 разрешённых
комплектах закупочных документов. Он нужен для приёмки стабилизации S4 и не
является заявлением о качестве распознавания, которого пока не измеряли.

## Цель и границы

Проверяем путь:

```text
байты документов → immutable extraction → mapping требований и completeness
→ кандидат и полное КП → ProcurementCase → evaluation → recommendation
```

Комплект (`document set`) — одна закупочная процедура со всеми файлами,
которые доступны проверяющему: ТЗ и приложения, КП и приложения к нему. Один
комплект имеет один `set_id`, но может содержать несколько исходных файлов.
Комплекты должны быть разрешены владельцем данных к локальной обработке.

Пилот проверяет полезность и безопасную границу автоматизации. Он не выдаёт
юридическое заключение, не отправляет КП/заявку, не открывает внешние сайты и не
меняет policy или permissions. Все внешние и юридически значимые действия
остаются за человеком и требуют exact-payload approval.

Отдельный пилотный результат не объявляется production-допуском. Он может
подтвердить только зафиксированные в отчёте условия, выборку и ревизию кода.

## Ответственные и независимость

До начала заполняются `pilot_owner`, `data_owner` и `ground_truth_reviewer`.
Владелец пилота организует запуск и хранит отчёт. Владелец данных подтверждает
разрешение и удаление/маскирование. Проверяющий эталона должен просмотреть
исходные документы и не должен принимать сгенерированные системой метки как
истину.

Один человек может совмещать роли только если это явно записано в manifest.
Тот, кто готовил AI-разметку, обязан отдельно перепроверить её по исходным
страницам. AI-разметка, подсказки LLM и результат OCR являются кандидатами для
проверки; ground truth создаётся человеком по исходным байтам.

## Выборка и manifest

Размер выборки: от 10 до 20 комплектов, включая как минимум один комплект
каждого реально поддерживаемого формата и известные трудные случаи. Если в
доступных разрешённых данных нет нужного класса, это записывается как пробел,
а размер выборки не увеличивается синтетическими документами без отдельной
пометки.

Рекомендуемая стратификация:

| Класс | Что включить |
|---|---|
| обычный | нативный DOCX/PDF/XLSX с таблицами и текстом |
| неоднозначный | единицы, диапазоны, отрицание эквивалента, даты или противоречия |
| скан | raster-only PDF, включая поворот/низкий контраст, если разрешено |
| вложения | архив или DOCX с приложенным изображением, если поддержано текущим pipeline |
| КП-ловушка | документ поставщика, текст которого похож на требования |

Manifest хранится только в `samples/private/` и не коммитится. Для каждого
комплекта обязательны следующие поля:

```json
{
  "manifest_version": "pilot-v1",
  "set_id": "private-001",
  "permission": {
    "status": "APPROVED",
    "scope": "local_pilot",
    "source": "<internal permission reference>",
    "approved_at": "2026-09-16T12:00:00+03:00",
    "expires_at": null
  },
  "procedure_reference": "<internal reference>",
  "files": [
    {
      "file_id": "private-001-tender-01",
      "relative_path": "private-001/tender.docx",
      "role": "TENDER_REQUIREMENTS",
      "media_type": "application/vnd.openxmlformats-officedocument.wordprocessingml.document",
      "sha256": "<64 lowercase hex>",
      "byte_size": "<integer>",
      "page_or_unit_count": "<integer or null>"
    }
  ],
  "expected_difficulty": ["table"],
  "ground_truth_status": "PENDING",
  "notes": "<no secrets or unnecessary personal data>"
}
```

В реальном manifest нельзя оставлять фиктивные значения из примера. `sha256`
считается по фактическим байтам; путь относительный и остаётся внутри
`samples/private/`. Нельзя включать абсолютные пути, секреты, cookies, API
ключи, персональные данные, которые не нужны для сценария, или содержимое
документов в Git. Нельзя повторять один source digest под разными `file_id`.
Разрешение должно покрывать именно локальную обработку, хранение производных и
срок пилота.

## Человеческий эталон

До просмотра результата системы два человека (или один с независимой второй
проверкой, что отмечено в отчёте) заполняют для каждого комплекта:

1. полный список существенных требований ТЗ с ролью (`mandatory`/`optional`),
   оператором, нормализованным значением и точным locator (файл, страница,
   лист/ячейка, абзац или строка);
2. список фрагментов, которые не являются требованиями, и обоснование
   исключения;
3. ожидаемые факты кандидата и КП, включая цену, валюту, состав комплекта,
   сроки, validity и подтверждающие документы;
4. ожидаемый результат каждого gate: только `PASS`, `FAIL` или `UNKNOWN`, с
   причиной и ссылкой на источник;
5. ожидаемую итоговую рекомендацию и блокирующее основание.

Если факт нельзя надёжно установить по документу, эталон обязан быть
`UNKNOWN`. Отсутствие требования в распознанном выводе не означает, что его
нет в исходном документе. После заполнения эталона исходные файлы не меняются;
изменение байтов создаёт новую версию `set_id`/digest и новый эталон.

Минимальная строка эталона:

```text
set_id | requirement_id | source_file | locator | expected_value
       | mandatory | expected_state | rationale | reviewer | reviewed_at
```

## Порядок выполнения

### 1. Зафиксировать окружение

Записать Git revision, дату и timezone-aware время запуска, версию Python,
версию PostgreSQL и настройки OCR. Секреты в отчёт не попадают. Перед запуском
проверить, что все файлы manifest существуют, их SHA-256 совпадают, разрешение
действительно и в рабочем дереве нет случайно добавленных приватных файлов.

Поддержанные команды репозитория:

```powershell
uv sync --extra dev
docker compose up -d postgres
./scripts/verify-postgres.ps1
```

Последняя команда — обязательный storage gate; обычный запуск
`uv run pytest tests/integration -q` допускает пропуски без `DATABASE_URL` и
сам по себе не считается доказательством. OCR extra и локальный model root
настраиваются отдельно согласно [pipeline](../documents/19-document-pipeline.md); наличие
модели не является результатом калибровки.

### 2. Проверить исходные байты и extraction

Для каждого файла зарегистрировать `file_id`, role, media type, digest и
размер. Передать файл в поддержанный pipeline с доверенной ролью
`TENDER_REQUIREMENTS` или `SUPPLIER_QUOTE`; неизвестная роль блокирует mapping.
Зафиксировать `ExtractionResult`: статус, причины, число units, extractor,
версии и provenance каждого сегмента.

Текущий репозиторий поддерживает серверную загрузку multipart через
`POST /v1/document-bundles` с полями `file`, `document_role` и заголовком
`Idempotency-Key`, а также чтение результата через
`GET /v1/document-bundles/{bundle_id}`. Точный запуск сервера и PostgreSQL
описан в [S2](17-storage-api.md). Для локального machine-only прогона
requirements understanding есть `scripts/run-tz-understanding-pilot.py`; он не
записывает server-side snapshots, не создаёт human ground truth и не заменяет
API/UI-путь полного пилота.

Если PDF получил `UNKNOWN/OCR_REQUIRED`, вызвать поддержанный endpoint OCR для
конкретного bundle/member после проверки разрешения и записать производную как
новую immutable-версию. Если OCR недоступен или confidence недостаточен,
сохранить `UNKNOWN`; текст нельзя додумывать.

### 3. Сопоставить требования и проверить полноту

Для каждого комплекта выгрузить mapping в строгую схему и сверить его с
человеческим эталоном. Зафиксировать каждое `mapped`, `unmapped` и
противоречие, включая locator и confidence. Отдельно записать completeness:
какие страницы/листы/разделы проверены, какие исключены и почему.

Пустой mapping, пустое извлечение или наличие существенного `unmapped` не дают
`PASS` полноты. При невозможности доказать объём проверки полнота равна
`UNKNOWN`, а автоматический допуск запрещён. КП не может создавать отсутствующее
требование ТЗ: роль `SUPPLIER_QUOTE` остаётся `unmapped` на этапе requirement
mapping.

Для одного полного native-документа есть persisted snapshot и независимое
решение через completeness-review API и внутренний `/completeness-review`.
Этот путь не покрывает ZIP, OCR, embedded media и multi-document комплект.
Создание независимого эталона и сверка всего комплекта остаются ручным gap;
не подменять их machine runner или golden tests.

### 4. Построить кандидата, КП и кейс

На основании подтверждённых человеком данных создать кандидата и полное КП,
связанные с той же компанией и процедурой. КП должно иметь provenance,
действующий срок и покрывать весь комплект. Деньги вводятся строками и
проверяются на сопоставимой базе; НДС и расходы задаются явно, расчёты ведутся
через `Decimal`. Deadline и `effective_at` всегда timezone-aware.

Для каждого комплекта сохранить снимки требований, кандидата, КП, профиля и
сценариев экономики. Не редактировать старый snapshot после появления
исправления; исправление создаёт новую версию.

Текущая поддержанная запись — `POST /v1/cases`, затем серверная оценка через
`POST /v1/cases/{case_id}/versions/{version}/evaluations` с новым
`Idempotency-Key`. UI S3 выполняет тот же импорт полного `ProcurementCase`.
Отдельные формы автоматического построения кандидата/КП из extraction пока не
предоставлены; сбор этих объектов из проверенного эталона — ручной gap, который
обязательно указывается в отчёте.

### 5. Получить recommendation и записать наблюдение

Оценивать каждый кейс на зафиксированный `effective_at`. Записать не только
итог, но и все gate states, основания, provenance, completeness, применённый
ruleset/engine version и audit/evaluation identifiers.

`FAIL` обязательного требования блокирует кандидата, `UNKNOWN` не превращается
в `PASS`, рейтинг не перекрывает hard gate, а процент соответствия при
mandatory `FAIL` не показывается. `PARTICIPATE` допустим только при полном
действующем КП и завершённых `base`, `realistic`, `conservative`. Внешняя
отправка, подпись или юридическое действие в пилоте запрещены.

### 6. Сверить с эталоном и провести негативный контроль

Проверяющий сравнивает результат системы с эталоном по каждой строке, а не
только по итоговой рекомендации. Для каждой ошибки указывается тип:
`extraction`, `mapping`, `completeness`, `candidate`, `quote`, `economics`,
`policy` или `presentation`; сохраняется ссылка на исходный locator.

Минимум один комплект должен быть повторно обработан с намеренно изменённым
байтом или одним изменённым входным полем. Ожидается новый digest/snapshot и
неприменимость старого evaluation. Минимум один межтенантный guessed-ID и один
replay/conflict проверяются на PostgreSQL gate, если они входят в выбранный
server path. Эти проверки не дают права публиковать внешние данные.

## Метрики и правила расчёта

Все знаменатели и исключения записываются. Метрики не вычисляются по
AI-разметке без человеческой проверки.

### Ложный PASS

Основная метрика — `false_pass_count`: число случаев, когда система выдала
положительный gate или рекомендацию, а human ground truth содержит
`FAIL`/недопустимый `UNKNOWN` для обязательного условия либо неполную
проверку. Цель приёмки: **0**.

Любая ошибка, сначала замеченная человеком после `PARTICIPATE`, считается
ложным PASS независимо от рейтинга. Если система выдала `UNKNOWN`, а человек
ожидал `PASS`, это не false PASS; это отдельная ошибка полноты/полезности.

### Recall существенных требований

```text
material_requirement_recall =
  правильно найденные существенные требования /
  все существенные требования в human ground truth
```

Считать по требованиям, а не по строкам OCR. В основной отчёт вынести
микроусреднение по всем комплектам и таблицу по каждому комплекту. Цель и
доверительный интервал до запуска фиксируются владельцем продукта; отсутствие
заданной цели означает `UNKNOWN`, а не автоматическую приёмку.

### Корректность provenance

```text
provenance_correctness =
  факты с правильным file digest и locator /
  все проверяемые факты, выданные системой
```

Неверный digest, файл, страница, лист, строка или extractor считается ошибкой.
Факт без provenance считается некорректным. Отсутствие provenance у
неположительного результата тоже фиксируется, даже если итог случайно
безопасен.

### Ручное время

Для каждого комплекта измерять timezone-aware `started_at` и `finished_at` для
двух интервалов: полного ручного разбора и разбора с системой до проверенного
решения. Записывать активное время и ожидание отдельно. Нельзя приписывать
системе сэкономленное время, если шаг выполнен вручную из-за текущего gap.
Сравнение является описательным при выборке менее 10 сопоставимых комплектов.

Дополнительно считать количество ручных исправлений, `UNKNOWN` по этапам,
время до первого объяснимого блокера и число комплектов, дошедших до полного
кейса. Эти показатели не заменяют нулевой false PASS.

## Приёмка пилота

Пилотный slice считается принятым только если одновременно выполнены условия:

- обработано 10–20 разрешённых комплектов, manifest, digests и permission
  проверены;
- для каждого комплекта есть независимый человеческий эталон с locator;
- путь от фактических bytes до extraction, mapping, completeness, case и
  recommendation воспроизводим для зафиксированной ревизии;
- `false_pass_count = 0`;
- существенные `unmapped`, неполное извлечение и неопределённость остаются
  `UNKNOWN` и блокируют автоматический допуск;
- provenance каждого принятого факта корректен либо кейс не принят;
- полный КП, три сценария экономики, Decimal, deadline и tenant scope
  подтверждены для кейсов, где получена recommendation;
- PostgreSQL gate пройден без пропусков, если использован server path;
- измерены manual time и material requirement recall, а цель recall и
  ограничения выборки явно указаны;
- ни один внешний/юридический payload не отправлен и не одобрен скрыто;
- отчёт прошёл вторичную проверку, а приватные данные не попали в Git,
  логи или итоговый публичный документ.

Если хотя бы один пункт не доказан, статус пилота — `UNKNOWN` или `FAIL` с
причиной; статус `PASS` не выводится по совокупности косвенных признаков.

## Шаблон итогового отчёта

```markdown
# Pilot report <pilot_id>

- status: PASS | FAIL | UNKNOWN
- manifest: <relative private path>
- manifest_sha256: <digest>
- code_revision: <git revision>
- started_at: <timezone-aware>
- finished_at: <timezone-aware>
- pilot_owner: <id>
- data_owner: <id>
- ground_truth_reviewer: <id>
- sample_count: <integer>
- allowed_scope: <permission reference, no document contents>
- environment: <python/postgres/ocr versions>

## Coverage

| set_id | files | roles | source digests checked | extraction | mapping | completeness | case/evaluation | recommendation |
|---|---:|---|---|---|---|---|---|---|

## Metrics

- false_pass_count: <integer>
- material_requirement_recall: <value or UNKNOWN>
- provenance_correctness: <value or UNKNOWN>
- manual_time_without_system: <value>
- manual_time_with_system: <value>
- manual_time_comparability: PASS | FAIL | UNKNOWN
- unknown_by_stage: <counts>
- corrections_by_type: <counts>

## Deviations and gaps

<manual gaps, unsupported formats, excluded pages, missing PostgreSQL/OCR,
conflicts, and why they prevent PASS where applicable>

## Evidence index

<relative private paths, API ids, audit/evaluation ids, and command output
digests; no secrets and no raw document content>

## Decision

<PASS/FAIL/UNKNOWN rationale, limitations, and one next bounded slice>
```

Таблица покрытия и evidence index должны ссылаться на приватные артефакты по
относительным путям и digest. В публичный отчёт выносятся только агрегаты,
идентификаторы и причины; исходные документы, OCR-текст, КП и персональные
данные остаются в защищённом хранилище с ограниченным доступом.

## Проверка самого протокола

Файл проверен как UTF-8 Markdown: все fenced code blocks закрыты, таблицы имеют
