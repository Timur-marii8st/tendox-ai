# 03. Движок соответствия — методика

Это ядро продукта. Всё остальное можно скопировать за месяц; доказательная
проверка соответствия — нет.

## Принцип

> LLM извлекает. Правила решают.

Движок соответствия — **детерминированный код**, а не промпт. Он получает уже
структурированные требования и атрибуты и не имеет доступа к языковой модели.
Обоснование — [adr/0002-llm-extracts-rules-decide.md](../adr/0002-llm-extracts-rules-decide.md).

Этот движок отвечает только на вопрос о соответствии товара/работы/услуги
требованиям. Допуск участника, законность, коммерческие запреты, экономика, риск
и рейтинг рассчитываются отдельно. Их нельзя усреднять в «общий процент».

## Три состояния

| Вердикт | Когда | Что показываем |
|---|---|---|
| `PASS` | Значение атрибута известно и удовлетворяет оператору | ✅ + источники обеих сторон |
| `FAIL` | Значение известно и НЕ удовлетворяет | ❌ + требование, факт, оба источника |
| `UNKNOWN` | Атрибута нет, не распознан, или уверенность ниже порога | ⚠️ «нужно уточнить у производителя» |

`UNKNOWN` никогда не сворачивается в `PASS`. Это главный источник ложной
уверенности в подобных системах: «характеристика не указана» — это не «подходит».

## Hard gate

```
if любое mandatory-требование == FAIL:
        вердикт кандидата = FAIL
        процент соответствия НЕ показывается
```

На уровне закупочного кейса действует более широкий порядок gates: deadline →
legal eligibility → participant eligibility → technical compliance → company
policy → подтверждённое КП → realistic economics. Только после них считается
рекомендация; рейтинг не может изменить результат gate.

Почему запрещён процент при провале hard-требования: карточка «96% соответствует»
с проваленной гарантией читается человеком как «почти идеально», хотя на деле это
гарантированное отклонение заявки. Показ процента здесь — не неточность
интерфейса, а дезинформация, ведущая к финансовым потерям.

Если есть `UNKNOWN` по обязательному требованию, вердикт кандидата —
`NEEDS_CLARIFICATION`, и это отдельное состояние: кандидат ещё жив, но требует
уточнения у производителя. Именно из этих пробелов RFQ Agent строит вопросы.

## Soft score

Считается **только среди кандидатов, прошедших все hard gates**:

```
soft_score = Σ(weight_i × passed_i) / Σ(weight_i)     по желательным требованиям
```

`UNKNOWN` в желательном требовании даёт 0 баллов, но не убивает кандидата.

## Итоговый вердикт кандидата

```
        ┌─ есть FAIL по mandatory ──────────▶ FAIL
        │
        ├─ есть UNKNOWN по mandatory ───────▶ NEEDS_CLARIFICATION
        │
        └─ все mandatory PASS ──────────────▶ COMPLIANT (+ soft_score)
```

Три числа, которые видит пользователь, никогда не смешиваются:
**соответствие** (вердикт), **экономика** (маржа), **риски** (категории и уровни).
Отдельный рейтинг привлекательности 0–100 разрешён для сортировки по ТЗ,
но не усредняет эти проверки и не отменяет обязательные ограничения.
Цвет карточки берётся из Recommendation.color, а не из числа баллов.

## Формат объяснения

Каждый `FAIL` и каждый `UNKNOWN` отображается полностью:

```
❌ Гарантия
   Требование ТЗ:  ≥ 24 мес.        источник: ТЗ.pdf, стр. 16
   Факт по товару: 12 мес.          источник: КП №42, стр. 3
   Требование обязательное — товар не проходит ТЗ.

⚠️ Класс защиты корпуса
   Требование ТЗ:  IP54             источник: ТЗ.pdf, стр. 15
   Факт по товару: не указан        источник: datasheet XXX-24G
   Нужно уточнить у производителя.
```

Для известного факта нужны обе ссылки. При отсутствии факта показываются
UNKNOWN, источник требования и «нет данных» со следующим вопросом поставщику.
Скрывать такой вывод нельзя.

Положительный результат по найденным требованиям не доказывает полноту ТЗ.
В document workflow `COMPLIANT` разрешён только при отдельном
`CompletenessAssessment.PASS`; `UNKNOWN` или провал completeness оставляет
кандидата в `NEEDS_CLARIFICATION`. Уже доказанный mandatory `FAIL` при этом не
скрывается.

## Особые типы проверок

| Тип | Как проверяем | Чего не делаем |
|---|---|---|
| Числовое, включая `EQ`/`NE` | нормализация единиц → проверка размерности → оператор сравнения | не сравниваем только числа при разных, неизвестных или отсутствующих единицах |
| Перечисление | значение ∈ допустимое множество | не считаем похожесть текста |
| Сертификат / декларация | явное требование ТЗ + документ совпадающего вида, действующий на дату поставки | не верим упоминанию в описании и не создаём gate из нерелевантного документа кандидата |
| ГОСТ | конкретная редакция + подтверждающий документ | не матчим подстроку «ГОСТ» |
| КТРУ / ОКПД2 | сверка с каталогом | не угадываем код по названию |
| Страна происхождения | явное подтверждение | не выводим из названия бренда |
| Эквивалент | разрешён ли в ТЗ, затем полная проверка по характеристикам | не подставляем аналог молча |

Срок действия сертификата проверяется **на дату поставки**, а не на сегодня.
Явное требование хранится как `certificate:<вид>` с оператором `EXISTS` и
provenance формулировки ТЗ. Если документ не представлен, дата поставки
неизвестна, confidence источника ниже порога или срок действия не указан,
результат остаётся `UNKNOWN`. Документ совпадающего вида, просроченный на дату
поставки, даёт `FAIL`; действующий — `PASS`. Само наличие в данных кандидата
просроченного документа не создаёт требования, которого нет в ТЗ.

Числовые `EQ` и `NE` подчиняются тем же правилам единиц, что диапазоны и
неравенства. Например, `24 мес == 2 года` даёт `PASS`, а `24 мес` против
`24 дней` или числа без единицы — `UNKNOWN`. Несопоставимость не инвертируется
оператором `NE` в положительный результат.

## Порог уверенности

Атрибут, извлечённый с уверенностью ниже порога (стартовое значение 0.75 —
калибруется на золотом наборе), в проверку не попадает: требование получает
`UNKNOWN`. Лучше задать производителю лишний вопрос, чем проиграть заявку.

## Как проверяем сам движок

Золотой набор реальных обезличенных ТЗ с разметкой вручную. Главная метрика —
не accuracy, а **ноль ложных `PASS`**: пропущенное несоответствие стоит клиенту
контракта, лишний `UNKNOWN` стоит одного письма.

```
приоритет метрик:
1. false PASS rate         → должен быть 0
2. recall обязательных требований при извлечении
3. доля UNKNOWN            → снижаем, но никогда за счёт п.1
```

## Частичная проверка серверного BOM

`procurement.domain.server_bom.assess_server_bom` — диагностическая проверка
конкретного состава сборки, не замена проверки полного ТЗ. Входом служат
`ServerBom` с SHA-256 документа состава, строками установленных деталей
(роль, SKU, количество, locator) и атрибутами с отдельными источниками;
требования также обязаны нести provenance. Поддерживаются семь числовых gates:
ядра каждого CPU, ёмкость каждого SSD, мощность каждого БП, число SSD и БП,
число передних LFF-отсеков и OCP-слотов конкретного шасси. Формулы для
нескольких деталей применяются к **каждой установленной** детали, не к
максимуму каталожного семейства. `Гбайт` приводится к `ГБ`.

`InventoryScope.PARTIAL` — значение по умолчанию: если перечисленных деталей
меньше требуемого, результат по количеству `UNKNOWN`. `EXACT_CONFIG` разрешён
только после проверки, что документ действительно перечисляет весь состав
конкретной конфигурации; тогда недостающее количество даёт `FAIL`. Это
утверждение вызывающего workflow, не автоматически доказанный факт. Низкая
уверенность, отсутствие свойства или несовместимые единицы дают `UNKNOWN`.
Доказанный обязательный `FAIL` имеет приоритет над другими `UNKNOWN`.

Все поддержанные gates могут получить частный `PASS`, но общий результат
`BomAssessment` всё равно остаётся `UNKNOWN`: 87 строк серверного приложения,
основное ТЗ, совместимость опций, полнота документов и независимый review
здесь не проверяются. Неподдержанные требования и отсутствующие gates явно
возвращаются в результате. В текущем срезе нет API, persisted review,
автоматического чтения BOM/КП или допуска кандидата к участию.
