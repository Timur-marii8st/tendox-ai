# Аудит стратегии получения и сравнения ЕИС

Дата: 2026-10-01 (МСК). Наблюдения серверного источника: 30.09, UTC.
Владелец: основной Codex. Срез S131, исследование и исправление сообщений.
Основание: PRD 3.1–3.5, ADR 0044, S120–S130, read-only проверки сервера,
первичные документы источников. Секреты и содержимое `.env` не публикуются.

## Вывод

Основа проекта подходит: официальный машинный канал, версионный индекс,
поиск по индексу, точная проверка номера и очередь выбранных документов.
Приоритет следует изменить: сначала свежие действующие закупки и проверка
качества поиска, затем история для конкуренции. Годовой backfill и массовый
HTML-обход не должны задерживать работающий сценарий запроса поставщика.

Рекомендуемый путь — объединять локальный индекс с быстрым поисковым
адаптером, проверять выбранные номера в ЕИС и глубоко анализировать ограниченный
список. Сторонний API может ускорять обнаружение, но не подменяет доказательство
официальной версии, срока и состава документации. Полный охват остаётся UNKNOWN.

## 1. Что действительно работает

Read-only снимок сервера `2026-09-30T20:44:10Z`:

| Метрика | Наблюдение | Граница вывода |
|---|---:|---|
| XML-версии | 45 137 | Сохранённые версии, не число закупок во всей ЕИС |
| Текущие известные карточки | 42 602 | Текущие внутри нашего индекса, свежесть относительно ЕИС не доказана |
| Импортированные окна | 1 498 | Конкретные регион/тип/дата, не все регионы и процедуры |
| События процедуры | 1 417 | Отмены уже встречаются в live данных; остальные семейства не покрыты |
| Задания документов | 7 | Все семь имеют скачанный перечисленный набор; полнота требований UNKNOWN |
| Blobs / analyses | 39 / 39 | Нативное извлечение не равно проверке всех условий |
| Байты вложений | 4 062 283 | Около 4 МБ для выбранных комплектов |
| Размер PostgreSQL | 1 109 670 935 | Около 1,03 GiB, включает архивы, XML, индексы и служебные данные |

Официальный importer принимает четыре типа PRIZ/44-ФЗ: электронный аукцион,
электронные котировки, отмену и отмену отмены. Полноценный импорт 223-ФЗ,
других способов, протоколов и истории контрактов ещё не готов.
Номера регионов 01–99 в плане не заменяют официальный каталог доступных регионов.

Индекс с GIN действительно ускоряет ограниченные запросы: ранее narrow-query
benchmark на синтетических 50 000 карточек дал около 49–54 мс вместо 6,7 с.
Это доказательство ускорения метаданных; оно не измеряет полноту, скачивание,
OCR, экономику или время всего пользовательского сценария.

Обнаружены два ограничения обновления:

- Дневное планирование заканчивается вчерашней датой. Для свежих публикаций
  текущего дня нужна отдельная recurring очередь, независимо от backfill.
- Успешный checkpoint закрывает окно и исключает его из очереди. Для поздно
  появившихся данных нужна повторная сверка с новым номером поколения загрузки,
  при сохранении immutable evidence прежних попыток.

`eligible_windows` ставит неиспытанные окна раньше повторных и сортирует даты
внутри этого порядка. Это полезно для backfill, но не гарантирует свежесть при
длинной очереди. План 144 540 окон и запуск до 60 окон раз в 15 минут — параметры
очереди, а не доказательство покрытия или фактической скорости всей загрузки.

## 2. Что показали дополнительные проверки публичного поиска

Запрос `бумага`, 44-ФЗ + 223-ФЗ, только `af` (подача заявок).
Сравнивались **номера закупок**, а не только HTTP, объём HTML или номер страницы.
Полный URL и минимальный URL проверены отдельно; в форме ЕИС отражались
правильные фильтры и номера страниц. Дополнительное ожидание 3 с не меняло набор.

| Размер | Проверенные страницы | Результат |
|---|---|---|
| 50 | 1, 2 | По 50 уникальных номеров; пересечение 0 |
| 100 | 1, 2, 11 | По 100 уникальных номеров; все три набора попарно не пересекаются |
| 200 | 1, 2, 6; полный URL страницы 2 | Везде один и тот же набор 200 номеров |
| 201, 250, 300, 1000 | Первая страница, S130 | По 10 карточек, несмотря на HTTP 200 |
| 500 | Первая страница, S130 | 200 карточек; неоднозначная обработка параметра |

Причина повтора при 200 не установлена: гипотезы о нормализации параметра,
сессионной логике и кешировании требуют отдельного опыта. Нельзя объявлять
общий предел ЕИС или переносить наблюдение на любой запрос.

Практические выводы:

- `_200` подтверждён для **первой** страницы, но непригоден как доказанный
  режим последовательного обхода. Production сейчас использует 200:
  многостраничный workflow требует следующего исправления.
- `_100` — кандидат для обхода: есть проверенные разные страницы, включая 11.
  Нужны повторные тесты, соседние границы, последовательная нумерация и
  остановка при одинаковом наборе. `_50` остаётся запасным проверяемым режимом.
- 20 видимых ссылок не доказывают 20 страниц всей выдачи. Предыдущий опыт
  страницы 21 с HTTP 200 и 50 карточками **не проверял уникальность**:
  утверждение о доказанном продолжении в S129 отзывается.
- Счётчик «более 15 000» является нижней границей заявления источника,
  а не точным числом действующих релевантных закупок или доступных страниц.
- SHA HTML меняется даже при одинаковых закупках. Нужен fingerprint отсортированных
  номеров и версии/профиль запроса; один SHA HTML повтор страницы не ловит.

### ГосПлан: что проверено, а что обещает поставщик

Это сторонний сервис, оператор — ИП; название не делает его государственным.
[OpenAPI](https://swagger.gosplan.info/) версии 2.4.0 описывает
`/fz44/purchases` и `/fz223/purchases`, `limit <= 100`, `skip`,
`object_info`, OKPD/КТРУ и фильтры дат. При текстовом запросе сортировка по
релевантности: `sort` не применяется. Необходимо задавать scope явно;
`published_forpast` нельзя путать с несуществующим `published_for`.
Полезная карточка по номеру не заменяет точные XML bytes для нашего evidence.

Read-only тесты `v2test.gosplan.info`, 30.09 UTC:

| Запрос | Ответ | Время одного вызова | Байты |
|---|---|---:|---:|
| Бумага, 44-ФЗ, stage=1, limit=100 | 100 номеров | 1,90 с, повтор 1,25 с | 95 528 |
| Та же выборка, skip=100 | 100 других номеров, пересечение 0 | 1,28 с | 96 428 |
| Бумага, 223-ФЗ, stage=1, limit=100 | 100 номеров | 0,83 с | 67 602 |
| Сервер, 44-ФЗ, stage=1, limit=20 | 20 номеров | 0,64 с | 20 140 |
| Известный номер `0848300054826000154` | JSON карточки, 1 документ | 0,30 с | 22 957 |

У первых двух порций номера сравнивались, а период по умолчанию не подтверждён.
Ошибочный дополнительный параметр `published_for=12m` в этих тестах не входит
в контракт и **не доказывает** годовой scope. Отдельный запрос с явным
`published_after=2024-10-01T00:00:00+03:00` и действующим deadline вернул
те же первые 100 номеров за 6,75 с; следующие вызовы получили HTTP 429.
Следовательно, 0,3–1,9 с нельзя обещать как SLA, а тестовый сервер нельзя
использовать для production нагрузки. Нужны общий token bucket, Retry-After /
backoff, остановка очереди при ограничении и измерение p50/p95 с разрешённой
нагрузкой. Вызовы после обнаруженного ограничения прекращены.

`19a9f83f79b0eb78e206d5a2ce56e0bb9e330feb66c49de617e3ccf8f82efb6a`;

## 4. Как получать данные эффективнее

1. **Свежий metadata индекс всего выбранного публичного scope.** Приоритет
   текущим публикациям/изменениям/отменам; историческая загрузка имеет отдельный
   бюджет и не блокирует foreground запросы. Каталог закон × тип × регион,
   состояния окон, source lag и quarantine неизвестных XML обязательны.
2. **Поиск по запросу с несколькими источниками.** Локальный индекс + optional
   provider + HTML fallback. Объединение по закону/номеру/лоту/версии, явное
   происхождение и непроверенные остатки. Все keyword-варианты в общем rate budget.
3. **Управляемое расширение запроса.** Бумага → офисная бумага/А4/канцтовары,
   серверы → вычислительное/серверное оборудование, OKPD/КТРУ. Поиск по
   позициям и извлечённым ТЗ: заголовок «канцтовары» может содержать нужную бумагу.
   Текущий строгий title-match теряет такие закупки. Semantic retrieval добавляет
   кандидатов; точные обязательные требования проверяются отдельно.
4. **Официальная проверка первых кандидатов.** Привязать номер к свежей версии,
   статусу, timezone-aware deadline, лотам и manifest; не тратить скачивание на
   заведомо просроченное/отменённое. Для 223 нужен отдельный настоящий adapter.
5. **Документы по спросу.** Очередь, приоритет shortlist, кеш bytes по SHA,
   extract/OCR один раз на конкретные bytes+версию parser. При изменении комплекта
   инвалидировать прежний анализ. Непроверенные кандидаты видны пользователю.
6. **Разделить хранение.** Компактные поля/позиции и evidence references в PG;
   immutable сжатые исходники в объектном хранилище с tenant access. Удалять
   исходники ради скорости без retention/provenance policy нельзя. Размер
   корпуса оценивать по измеренным байтам/версии и темпу обновлений.
7. **Переработать transport после benchmark.** Сейчас новый Chromium и WSDL на
   окно. Проверить reuse одного browser/context и, при подтверждённой TLS/proxy
   совместимости, прямой SOAP HTTP transport. Bounded concurrency для скачивания,
   extraction/OCR и отдельных upstream budgets; не 100 браузеров на один сайт.
8. **Стабильные разбиения и overlap.** При лимите поисковой выдачи делить
   подтверждёнными фильтрами закон/даты/регионы/классификатор; повторять граничные
   интервалы и дедуплицировать. Завершённые подзапросы доказывают только свой
   scope; отсутствие независимого знаменателя оставляет полноту UNKNOWN.

## 5. Почему чтение карточек ещё не находит максимальную прибыль

НМЦК — потолок цены, а не доход поставщика. Нужны количество/единицы/полный
ассортимент, действительное полное КП, доставка, налоги, стоимость обеспечения,
финансирования и оплаты, гарантия/сервис, срок, ограничения допуска и ожидаемая
цена победы. Экономика считается Decimal в base/realistic/conservative.
Mandatory FAIL исключает кандидата до ранжирования; неизвестные данные не дают
PARTICIPATE. Сценарий запроса должен соединить существующие компоненты quote,
requirements, document review и economics с discovery, а не только показать
отдельные работающие экраны.

Для конкуренции нужны протоколы результатов и контракты, сопоставимые по
товару/региону/условиям/датам: число допущенных, снижение, победители, история
заказчика. Конкуренты текущей закрытой подачи могут быть неизвестны; нельзя
выдавать историческую оценку за известный состав текущих участников.
Explainability связывает каждую причину с номером, версией, документом/строкой,
ценой КП, временем чтения и явным допущением; LLM не заменяет проверку факта.

## 6. Рекомендуемая последовательность ограниченных срезов

Это новая очередь приоритетов, не заявление о готовности. Перед каждым срезом
назначаются один владелец, точные owned files и зависимости в live плане.

| Приоритет | Срез | Acceptance / gate |
|---|---|---|
| P0 | Исправить публичный обход | Fingerprint всех raw номеров; остановка/явная ошибка при повторе; счётчики total/unique/parsed; повторные 100/50, страницы 1/2/граница; ни URL, ни 200 HTTP не дают COMPLETE |
| P1 | Бенчмарк единого поиска | 20–30 запросов, серверы/бумага и синонимы; известные размеченные закупки, recall/precision, distinct pages, p50/p95, lag, байты и 429; providers без платной нагрузки |
| P2 | Свежесть существующего официального scope | Авторитетные каталоги регионов/типов; отдельный same-day lane + daily reconciliation для уже поддержанных семейств; версии/отмены/late arrivals; UI scope и lag |
| P3 | Optional provider adapter | После P1: tenant provenance, schema validation, явный период, deadline timezone, Decimal, quotas/circuit breaker, dedup и official by-number verification; лицензия подтверждена |
| P4 | Top-N полный анализ | На нескольких реальных запросах shortlist → все перечисленные документы → requirements → полное КП → 3 сценария; неполные наборы UNKNOWN; обновления инвалидируют решение |
| P5 | Расширение официального охвата | По одному семейству/adapter за срез: остальные целевые процедуры 44-ФЗ, 223-ФЗ, статусы и версии; XSD/live fixtures/replay; все известные пробелы явно отмечены |
| P6 | Конкуренция и проверка полноты | Официальные протоколы/контракты, качество сопоставления и calibrated uncertainty; сверка независимых источников в известном scope, разбор всех расхождений |
| P7 | Storage / transport tuning | На измеренной нагрузке reuse/direct transport/object storage; benchmark и бюджет, сохранённый replay/RLS/provenance |

Продуктовые цели для **будущего** benchmark: первые кандидаты до 5 с p95
при исправном upstream/кеше; базовое сравнение до 10 с p95; документы и глубокий
анализ асинхронно с измеряемым прогрессом. Это не обещание текущей системы.
Раздельно измерять time-to-first-result, полный scope traversal, metadata rank,
verified document analysis и готовое экономическое решение.

Критерий продвижения: полезный проверяемый результат по свежему запросу и
объяснимые пропуски. Число скачанных гигабайт само по себе не критерий готовности.
