# Получение свежего публичного корпуса ЕИС без полного архива вложений

Дата исследования: **2026-10-03, Europe/Moscow**. Владелец: Research subagent,
S166. Owned file: только этот документ. Зависимости: PRD §§3.1–3.5,
ADR-0044, docs/26/32/33/37/38 и состояние S165–S166 в docs/15.
Acceptance: первичные источники, различение фактов/выводов, сравнение каналов,
конкретный порядок расширения и проверка пропусков. Код, shared docs,
production SSH, API intake, регистрация и покупка подписок не выполнялись.

## Решение для продукта

**Рекомендация:** сохранить официальный `getDocsIP` как источник версий и
доказательств; направить ресурс на свежие извещения и события по широкому
географическому охвату. Для closed-day окон использовать дневные партии,
для свежего потока — часовые; каждый день повторно сверять вчерашние данные.
Документы получать и анализировать для релевантного shortlist. Provider API
может быстро добавить кандидатов вне нашего текущего индекса и начальный список
открытых процедур, затем точные номера проверяются в официальном канале.

Источник, уже разрешающий массовое получение **публичных** 44/223-ФЗ, есть.
Не установлено, что одна доступная выдача обеспечивает доказанно все текущие
публичные закупки по всем типам и регионам. Наличие машинного канала и
поддержка двух законов не доказывают полноту нашего приёма.

Цель — доступные поставщику действующие релевантные процедуры, а не история
ради истории. Однако «загрузить последние 30 дней» не равно «получить все
действующие»: более старая публикация может оставаться открытой или получить
продление. Нужны начальный active inventory и поток изменений, а для старых
известных незавершённых процедур — адресная перепроверка. Период bootstrap
без такой сверки остаётся явным ограничением охвата.

## Дневные и часовые партии: применимый расчёт

Официальный контракт поддерживает `exactDate` и `oneHourInfo`; начало часового
окна должно отставать более чем на два часа. При подготовке предусмотрен poll
с интервалом 10с, готовность проверяется перед скачиванием всех архивов.
Источник этих величин — ADR-0044 и официальный альбом выше.

**ВЫВОД:** для завершённого дня одно дневное окно вместо 24 часовых уменьшает
число начальных запросов до 24 раз при одинаковом scope. Это не обещание
24-кратной скорости: число архивов, размер, подготовка и parsing могут расти.
Слишком большой день следует делить на 24 часа и измерять размер/стоимость;
родительское окно нельзя закрыть успешно до завершения и сверки всех детей.
Достижение 1000 URL или ресурсного лимита — явный gap, не пустой успешный день.

Параметры расчёта: R — подтверждённые регионы, T — нужные families, C — среднее
число квотируемых операций на окно (начальный вызов и polls; правила учёта GET
архивов в квоте уточнять), S — средняя занятость последовательного worker.

- Hourly lane требует примерно R×T начальных окон/час плюс retry/reconcile.
- Daily lane: R×T окон/сутки, в среднем R×T/24 в час.
- Необходимые ограничения: R×T×C ниже эффективного часового бюджета и
  R×T×S ниже доступных worker-seconds/hour при последовательной обработке.
- Иллюстрация, **не подтверждение каталога 99 регионов**: R=99,T=5 даёт
  495 окон/час, допустимая средняя последовательная занятость <7,27с/окно.
  Если каждое окно реально занимает хотя бы10с, один последовательный worker
  такую нагрузку не обслужит, даже при свободной квоте запросов.
- NSI S145 содержит 27 public/actual PRIZ и67 RI223 типов; это не94 одинаково
  полезных извещения. Слепой hourly Cartesian product 99×94=9306 начальных
  запросов/час уже превышает4000/ч без polls. Нужна семантическая матрица типов.

Практический режим: свежие admitted notice/change/cancel families получают
отдельный бюджет; вчерашние сутки сверяются дневными окнами; старые даты
заполняются остаточным бюджетом. Нулевые окна не доказывают, что family можно
исключить навсегда. Редкие типы допускают менее частую загрузку только с явно
показанной задержкой и периодическим контрольным опросом.

Внешнюю квоту и shared lock менять только после измерения: request/poll/GET
count, prepared latency, compressed/expanded bytes, XML count, noData share,
lock occupancy и useful new current records по каждой family. Документированная
квота LE больше, но смена аккаунта сама по себе не исправляет worker bottleneck;
LE — отдельная разрешённая регистрация, не предложение обхода IP quota.

## Расширение типов и пропуски

Приоритет по существующим пробелам: остальные актуальные notice families223,
их изменения/отмены/продления и неизвестные важные семейства44. Конкретные
имена брать из pinned public/actual NSI и XSD, а не из названия способа.
Не все27/67 типов нужны для первичного обнаружения. Для завершённых процедур
протоколы полезны в status projection и конкуренции; массовый full-history
import протоколов не должен быть зависимостью первых результатов поиска.

Составить матрицу `law / subsystem / XML family / public / actual / schema /
parser / event semantics / regions / latest verified day / gaps`. Отдельно
показать supported, source observed but unsupported, rejected и not probed.
223-ФЗ «иной способ» из docs/38 — конкретный source-quality gap: один
невалидный member привёл к отказу архива. Следующее архитектурное решение
может разрешить хранение безопасных members с явным PARTIAL quarantine;
нельзя маркировать всё окно COMPLETE или превращать schema FAIL в PASS.

## Как доказать recall и задержку

Нужны четыре отдельные проверки; единый процент «покрытия ЕИС» скрывает ошибки.

1. **Транспорт окна:** точный scope/UID, terminal readiness, все URL и архивы,
   SHA, число XML, quarantine и resource limits. COMPLETE здесь означает
   полный обработанный ответ в известной границе, а не все публикации ЕИС.
2. **Сверка множества:** для фиксированного закона/региона/семейства/периода
   сравнить IDs+versions из day с объединением24hour после допустимого лага;
   повторить day на следующий день. Разности сохранять с причиной. Один
   эксперимент не доказывает все регионы, но обнаруживает плохой режим партий.
3. **Source recall:** собрать стратифицированный reference set номеров через
   официальную выдачу и разрешённый provider discovery, затем официально
   подтвердить каждый discrepant номер. Считать `found_in_index / verified_refs`
   отдельно по закону, региону, способу, давности и типу запроса. Это recall
   относительно выборки; без полного независимого denominator global UNKNOWN.
4. **Search recall:** среди одинакового exact-version корпуса сравнить retrieval
   с размеченной выборкой релевантных позиций/ТЗ. Заголовок «хозтовары» может
   скрывать бумагу. Пропуск ingestion, отсутствие parser family, слабый поиск
   и недочитанные документы должны иметь разные причины.

Время: хранить source publication raw/zone, first_seen_at, ingested_at,
last_reconciled_at; публиковать p50/p95/max задержки отдельно по scope.
Naive source timestamps223 нельзя автоматически считать UTC/МСК ради красивой
метрики. Быстрый read cached карточки не измеряет freshness.

Минимальный benchmark — несколько фиксированных товарных запросов (бумага,
серверы, стабилизатор, общая категория с нужным товаром только в позиции),
44/223, несколько регионов разной плотности, старые продлённые и отменённые
процедуры. Сохранить номера, версии, scope, время и расхождения; показать
сколько source candidates, сколько exact verified, сколько документов
получено и сколько остаётся UNKNOWN. Не назначать целевой95% без знаменателя.

## Bootstrap через провайдера и хранение

После разрешённого production доступа провайдера: получать сначала компактные
списки актуальных кандидатов по закону и сроку с явными временными фильтрами.
Не ограничиваться stage1: его семантика сторонняя, неизвестный timezone или
продление могут исказить active selection. Сохранять отдельный UNKNOWN пул.
К старым публикациям применять адресную сверку; не полагаться на default1m.

Для большого bootstrap разбивать по source date/region/type, сохранять
контрольный upper timestamp и повторять границы; без текстового relevance sort
обход предсказуемее. `skip` в изменяющейся коллекции не становится snapshot:
нужны дедупликация и повторная сверка partition. `updated_after` по дате ЕИС
не гарантирует обнаружение поздно загруженного документа со старой датой:
использовать overlap и периодическую сверку. Конкретные фильтры и timezone
проверить contract тестом до утверждения completeness.

Provider discovery objects отделять от официальных evidence records:
`provider / request scope / fetched_at / source identifier / hash / uncertainty`.
Только shortlist требует официального by-number XML, актуального manifest,
типизированных позиций и документов. Не переписывать официальный immutable
XML нормализованным JSON провайдера. Cache и лимиты общие;429 прекращает
нагрузку согласно Retry-After/backoff, не вызывает сменуIP.

**Терабайты сейчас не обоснованы.** В docs/32 измерены около1,03GiB PostgreSQL
для45137XML-версий и служебных данных, при вложениях выбранных семи комплектов
около4МБ. Это небольшой старый срез, не универсальная норма bytes/record.
Оценивать новый объём по `число XML-версий × measured mean compressed bytes +
проекции/индексы + shortlist attachments + WAL/backups/retention`, отдельно
измеряя тяжёлые хвосты. Не линейно экстраполировать7малых комплектов на всюЕИС.
Сжатые immutable исходники можно переносить в объектное хранилище с tenant
контролем; это отдельное решение retention/backup, не разрешение удалить evidence.

## Следующие последовательные срезы

1. Зафиксировать throughput свежего scope и причины отказов; убрать бесполезную
   idle contention (работа root S166). Acceptance: одинаковые quotas/gates,
   больше измеренных useful completed windows, а не только planned count.
2. Закрыть один важный новый223notice/event contract и протестировать дневное
   окно против24часов в малом scope. Acceptance: точная разность множеств,
   все archive outcomes, XSD/provenance и честный PARTIAL при quarantine.
3. Масштабировать текущие admitted families по подтверждённым регионам с
   day/hour capacity model; постепенно расширять типы по измеренным пробелам.
4. При разрешённом provider доступе выполнить bounded bootstrap/reconciliation
   proof. Покупка и сообщения поставщикам остаются отдельным действием.
5. Пройти end-to-end benchmark от запроса до shortlist с actual evidence;
   затем добавлять данные поставщиков и полную стоимость. История конкуренции
   получает отдельный scope и остаточный бюджет.

Пункты2–5 — предложения, не реализованный результат. Хороший discovery или
быстрые три предварительных сценария не дают `PARTICIPATE`: нужны reviewed
requirements, действительное полное КП, налоги/логистика/полная стоимость и
`base / realistic / conservative` по конкретному лоту. Mandatory FAIL
блокирует; критический UNKNOWN остаётся вопросом для проверки.
