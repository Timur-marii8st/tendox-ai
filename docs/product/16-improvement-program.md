# Программа улучшения продукта

Этот документ задаёт целевой контракт упорядоченной программы работ. Он не
подтверждает выпуск, качество поиска или полноту охвата ЕИС. Текущие статусы и
следующий выполняемый срез ведутся только в [live-плане](../15-implementation-plan.md);
подробные результаты и источники каждой итерации сохраняются как evidence.

## Основание и границы

Программа реализует поиск и анализ кейса по [PRD §§3.1–3.5](11-product-requirements.md#31-поиск):
точный и семантический поиск, разбор требований с provenance, подтверждённые
предложения поставщиков, три сценария экономики и решение после hard gates.
Источники, ограничения доступа и фактическое покрытие показываются явно.
«Все закупки» остаётся целью, пока официальный census поддерживаемого охвата и
независимая сверка с эталонными данными не подтверждены.

Действуют обязательные инварианты корневого [AGENTS.md](../../AGENTS.md):
`PASS | FAIL | UNKNOWN`, ноль допуска при обязательном `FAIL`, отсутствие
процента при mandatory `FAIL`, `Decimal` для денег, timezone-aware сроки,
tenant scope и exact-payload approval для внешних действий. Недостаток evidence
или неясная область дают `UNKNOWN`; оценка или агрегат не снимает hard gate.

## Milestones и зависимости

Приоритет изменён пользователем08.10.2026: удобный поиск публичных закупок44-ФЗ
и223-ФЗ по всей России, максимально доступная история и регулярное обновление.
Census и расширение загрузки M5 начинаются сейчас и не зависят от завершения
M2–M4. Принятые production6 и restore используются повторно без новой выгрузки.
Работа последовательными завершёнными срезами: production gap → исправление →
фактически новые данные → доступность в поиске → измеренный backlog/rate.
Независимые метрики M2 и UX/экономика сохраняются, но не задерживают ingestion.
Полный охват не заявляется по числу планов; scope сверяется с официальным каталогом,
неподдерживаемые публичные типы и неизвестные границы перечисляются явно.

## Предложенные цели качества

M1 допускает локальный автоматический workflow по [ADR-0107](../adr/0107-candidate-triggered-quality-gate.md):
submission каждого кандидата запускает полный неизбирательный policy, а local
run ID служит workflow run этого provider. Это не hosted PR/push CI. Bounded M1
принят после installed activation, двух полных runs, независимых audits и refusal
checks. Приёмка не переносится на следующий payload: commit/SHA, scope, сборка,
export/install-base evidence, receipt и exact-payload approval остаются обязательными.
Текущий национальный ingestion slice и подтверждённый rollout blocker —
[в census/evidence](../eis/ingestion/120-eis-national-coverage.md).

Это рабочие численные цели для согласования и последующей калибровки по
baseline; они не являются уже измеренными результатами или гарантией. Root
может менять их при фиксации M2, сохраняя причину и версию цели.

| Метрика | Предлагаемая цель и способ чтения |
|---|---|
| Поиск p95 | ≤ 5 секунд на замороженном наборе; учитывать успешные и неуспешные запросы, указывать окружение и границы измерения. Таймауты и ошибки включаются как завершённые наблюдения со временем до ошибки/таймаута; исключать их или считать только успешные ответы нельзя. |
| Precision@10 | ≥ 0.90 на независимо размеченном наборе M2. Для каждого запроса precision = релевантные уникальные результаты в первых 10 / `min(10, число уникальных фактически возвращённых результатов)`. Если у запроса есть эталонно релевантные результаты, но выдача пуста, это не исключается: запрос получает 0. Нулевой знаменатель при запросе без известных релевантных элементов отмечается отдельно и раскрывается в отчёте. |
| Known-reference recall | ≥ 0.95 только среди подтверждённых эталонных результатов в той же версии закона/режима, регионе и временном охвате. Учитываются только reference items, доказанно входящие в известный корпус. Недостающий в корпусе эталонный объект считается потерей покрытия/корпуса и показывается отдельно, а не как retrieval loss. Не трактовать метрику как recall «по всей ЕИС». |
| Критические ложные `PASS` | 0 на проверенном наборе hard gates. Любой найденный случай блокирует приёмку затронутого среза до исправления и повторной независимой проверки. |
| UX выполнение | ≥ 90% завершённых заранее определённых пользовательских задач; число ручных шагов измеряется на том же протоколе и публикуется как baseline/результат без неподтверждённой цели улучшения. |
| Свежесть источников | Измерять отдельно официальную задержку доступности у источника и системный ingestion lag: доступность официальной записи → её получение/индексация → показ. Цель задаётся только после подтверждения расписания/availability; задержку публикации источника нельзя приписывать ingestion системы. |

## Evidence, владельцы и передача

Перед началом каждого среза root фиксирует одного владельца, короткий brief,
owned files, acceptance, зависимости и проверку. Полную историю контекста не
передают; ADR и PRD указываются по конкретной ссылке. Владелец не редактирует
чужие owned files. Независимый reviewer получает только требуемую область и
остаётся read-only, если отдельно не назначен владельцем изменений.

Каждая handoff-запись содержит: milestone и owner; scope и commit/SHA; путь к
evidence и точную команду/CI run; результат и время проверки; набор данных и его
дату/версию; ограничения и оставшиеся `UNKNOWN`; зависимости; следующий шаг и
его acceptance. Без этих данных milestone остаётся незавершённым. Исправление
ошибки добавляется как новая запись со ссылкой на предыдущую, а не заменяет
историческое evidence.

Решение по milestone принимает root по acceptance и evidence. PASS действует
только внутри описанного scope и версии; FAIL фиксирует воспроизведение и
блокирующую причину; UNKNOWN фиксирует отсутствующее evidence и владельца
следующей проверки. Никакой milestone сам по себе не меняет policy, permissions
или границу автономии A3.
