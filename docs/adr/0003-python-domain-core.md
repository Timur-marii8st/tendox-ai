# ADR-0003. Python + pydantic для ядра домена

**Статус:** принято · **Дата:** 2026-08-30

## Контекст

Основная сложность продукта — разбор документов (PDF/DOCX/XLSX/OCR), работа с
LLM и структурированное извлечение. Нужен язык с сильнейшей экосистемой в этих
задачах и при этом пригодный для строго типизированного доменного ядра.

## Решение

Python 3.11+ с pydantic v2 для доменных моделей, FastAPI для API,
PostgreSQL 16 + pgvector как единое хранилище реляционного домена и векторного
поиска, `uv` для управления зависимостями, mypy в strict-режиме на пакете
`domain/`.

Слой `domain/` не выполняет I/O и не обращается к сети — он полностью тестируем
без БД, LLM и площадок.

## Последствия

Положительные: прямой доступ к лучшим библиотекам парсинга и LLM-тулингу;
pydantic даёт валидацию схем на границе с LLM бесплатно; одна БД вместо двух.

Отрицательные: Python медленнее на CPU-bound задачах — при росте объёмов
парсинга потребуются воркеры и, возможно, вынос горячих участков; strict mypy
на pydantic-моделях требует аккуратности.

## Альтернативы

- **TypeScript end-to-end.** Отклонено: слабее экосистема парсинга документов и
  OCR, а именно она определяет качество продукта.
- **Go для ядра.** Отклонено: выигрыш в производительности не окупает потерю
  скорости разработки и библиотек на этапе поиска product-market fit.
- **Отдельная векторная БД.** Отклонено как преждевременное усложнение:
  pgvector покрывает потребности до заметного масштаба.
