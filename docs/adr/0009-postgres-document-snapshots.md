# ADR 0009: PostgreSQL BYTEA для исходных документов в пилоте

Дата: 2026-09-09. Статус: принято для первого среза S4.

## Контекст

Целевой контур использует PostgreSQL для транзакционных данных и
S3-совместимое object storage для исходных документов. Для первого вертикального
среза нужен атомарный tenant-scoped приём документа вместе с digest, статусом
извлечения, provenance и audit. Внешнее object storage ещё не имеет рабочего
адаптера, а разрыв между записью метаданных и байтов усложнил бы проверку
неизменяемости и интеграционные тесты.

## Решение

В пилоте исходные байты каждой версии сохраняются в PostgreSQL `BYTEA` в
tenant-scoped неизменяемой записи с SHA-256, размером, MIME/сигнатурой и
статусом конвейера. Запись и её audit event создаются одной транзакцией.
UPDATE/DELETE запрещены на уровне приложения и базы для runtime-роли. Размер
ограничивается конфигурацией до записи; лимит распространяется на один входной
документ и не заменяет архивные guard-ы парсера.

Конвейер обращается к байтам через порт хранилища, а не напрямую связывает
доменный код с `BYTEA`. Переход на object storage выполняется отдельной
миграцией: сначала загружается объект по непрозрачному tenant-scoped ключу,
проверяется digest и доступность чтения, затем в транзакции фиксируется ссылка;
старые версии сохраняются до подтверждённой миграции и сверки digest.

## Последствия

Пилот получает простую атомарность, RLS-проверку и воспроизводимые тесты без
нового инфраструктурного сервиса. Цена решения — ограниченный размер файлов,
рост базы и меньшая пригодность для больших архивов. BYTEA не является целевой
моделью масштабирования и не разрешает хранить секреты вне tenant scope.

Ни хранение, ни извлечение не дают юридического или коммерческого вывода.
Неизвлечённый текст, включая сканированный PDF, остаётся `UNKNOWN`; внешние
действия по-прежнему требуют отдельного подтверждения точного payload.

## Альтернативы

Сразу подключить S3-совместимое хранилище — целевая архитектура, но для текущего
среза потребовало бы отдельного адаптера, lifecycle policy, проверки доступности
и сценариев согласованной очистки. Хранить только ссылку без байтов — дешевле,
но нарушает воспроизводимость приёма и делает доказательство версии зависимым от
внешней системы. Поэтому обе альтернативы отложены до миграционного среза.
