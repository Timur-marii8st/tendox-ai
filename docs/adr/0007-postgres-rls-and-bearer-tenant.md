# ADR 0007: tenant из bearer identity и защита PostgreSQL RLS

Дата: 2026-09-08. Статус: принято для S2.

## Контекст

S1 хранит локальный JSON без аутентификации и tenant access control. Для API
нельзя доверять переданному клиентом `company_id`. Проверка только в маршруте
оставляет риск при ошибке нового endpoint или фоновой задачи.

## Решение

Bearer credential серверно сопоставляется с `Principal(company_id, actor_id)`.
Tenant-контекст не принимается из отдельного заголовка или query-параметра.
Каждая транзакция runtime-репозитория устанавливает локальный PostgreSQL setting
`app.company_id`; все tenant-таблицы имеют RLS и `FORCE ROW LEVEL SECURITY`.
Runtime-роль не владеет таблицами и не получает `BYPASSRLS`.

Версии кейсов immutable. Evaluation загружает точную версию на сервере и пишет
результат с audit через одну сервисную границу. Записи имеют idempotency key.
Исходные API-ключи не хранятся, только digest; одинаковая ошибка аутентификации
не раскрывает существование ключа или tenant.

## Последствия

Изоляция проверяется и приложением, и PostgreSQL. Миграции используют отдельное
владельческое подключение; приложение — runtime URL. Тесты на SQLite не могут
подтвердить RLS, поэтому обязательны интеграционные тесты PostgreSQL.

Локальный bearer bootstrap не заменяет production IAM, TLS, ротацию и secret
manager. В S2 поддерживается один активный tenant на транзакцию; общий admin
endpoint намеренно не создаётся.

## Альтернативы

Tenant в `X-Company-ID` — подменяем клиентом. Только ORM-фильтры — легко забыть.
Одна схема/БД на tenant — сильнее изолирует, но усложняет ранний SaaS и миграции.
