# ADR-0018: Явная полнота извлечения требований документа

Дата: 2026-09-16  
Статус: принято

## Контекст

Детерминированный маппер доказывает происхождение каждого найденного требования,
но не доказывает, что нашёл все существенные требования документа. Пустой
результат может означать отсутствие требований, неподдержанный формат, потерю
текста при извлечении или отсутствие подходящего правила. Частично успешный
маппинг имеет ту же проблему: известные требования можно проверить корректно,
не заметив потерянное обязательное условие.

`unmapped` сохраняет непокрытые блоки, однако причина `NO_PATTERN_MATCH` сама по
себе не отличает заголовок от существенного требования. Поэтому число найденных
требований и доля mapped-блоков не могут служить положительным gate полноты.

## Решение

`FactMappingResult` получает отдельный типизированный
`CompletenessAssessment` со статусом `PASS | FAIL | UNKNOWN`. Автоматический
`map_blocks_to_requirements` всегда возвращает `UNKNOWN`; полное покрытие не
выводится из отсутствия `unmapped`.

Терминальные `PASS` и `FAIL` требуют review evidence: описание проверенного
scope, точные `source_document_ids`, reviewer, timezone-aware время и ссылку на
review record. Каждый рассмотренный `unmapped`-блок связывается с исходным
текстом и provenance и получает одно решение:

- `MATERIAL_REQUIREMENT` — существенное требование осталось неструктурированным;
- `NON_REQUIREMENT` — блок проверен и не задаёт требования;
- `EXCLUDED_FROM_SCOPE` — блок явно исключён из объявленного scope с основанием.

`PASS` разрешён только для документа с ролью `TENDER_REQUIREMENTS`, в котором
есть хотя бы одно формализованное `Requirement`, после решения reviewer по
каждому `unmapped`-блоку и при отсутствии `MATERIAL_REQUIREMENT`. Извлечённые
только срок поставки или режим эквивалента не считаются достаточным основанием
полноты. `FAIL` обязан ссылаться на точный существенный
`unmapped`-блок результата. Документы других ролей не могут получить
положительную или отрицательную оценку полноты требований ТЗ и остаются
`UNKNOWN`. Валидаторы также запрещают неполную review-привязку, naive datetime,
повторные решения и подмену source document относительно доступного в результате
provenance.

Интеграция выполняется поэтапно. Этот ADR вводит документный контракт и его
инварианты; compliance и case workflow должны отдельно потребовать
`completeness=PASS` перед автоматическим положительным допуском. До такой
интеграции `FactMappingResult` сам по себе не является решением о допуске.

Ручной S1 остаётся совместимым: ранее подтверждённые проверки кейса сохраняются
как ручные проверки. Им не приписывается автоматическая полнота задним числом;
для перехода на новый автоматический путь нужен отдельный completeness review,
привязанный к неизменённым входным документам.

## Последствия

- пустое или частичное извлечение не может молча стать доказательством полноты;
- служебные блоки можно исключить только явным решением с основанием;
- старые golden JSON без поля полноты загружаются как `UNKNOWN`;
- изменение document ID или provenance требует нового source binding;
- текущий контракт ещё не хранит review в PostgreSQL и не связывает его с
  digest точных bytes; для результатов только с флагами/датой он также не хранит
  provenance mapped-блока. Это отдельный persisted workflow;
- положительный compliance по известным требованиям не равен полноте документа,
  пока потребитель явно не проверяет новый gate.

## Альтернативы

- Считать отсутствие `unmapped` достаточным — отклонено: пустой или неполный
  extraction дал бы ложный положительный результат.
- Блокировать `PASS` при любом `unmapped` — отклонено: заголовки и служебный текст
  не являются требованиями, но их исключение должно быть доказуемым.
- Использовать только процент mapped-блоков — отклонено: один потерянный hard
  gate важнее любого процента покрытия.
- Сразу менять compliance и весь persisted workflow — отклонено для этого среза:
  сначала фиксируется узкий проверяемый документный контракт, затем его потребители.
