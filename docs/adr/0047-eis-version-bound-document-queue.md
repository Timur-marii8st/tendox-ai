# ADR 0047: очередь и кеш документов точной версии извещения

Дата: 2026-09-28. Статус: принято.

## Контекст

Поиск по XML стал быстрым, но документов большинства карточек ещё нет.
Повторная загрузка/извлечение при каждом сравнении увеличивает задержку.
Сохранённый разбор нельзя переносить на изменившийся XML без проверки версии,
а полный список скачанных файлов нельзя объявлять проверенным комплектом.

## Решение

Очередь находится в PostgreSQL вместе с индексом. Immutable job привязан к
tenant, номеру закупки, версии и SHA XML. Входом служит exact reference из
индексной карточки; оператор не передаёт произвольный URL/список файлов.
Планировщик проверяет оригинальный manifest и последнюю известную версию.
Повтор POST идемпотентен. Старые задания остаются evidence; worker пропускает
их, GET явно показывает STALE и текущую известную версию.

Четыре FORCE RLS таблицы: jobs, blobs, analyses, observations. Байты сохраняются
один раз на SHA внутри tenant. Каждая попытка получения — отдельная immutable
observation с UID, временем, SHA или кодом ошибки; URL, имя, размер и XML-локатор
берутся из связанной исходной версии. Audit фиксирует создание и получение.
Файл другого UID отвергается; полученная версия не переписывается другим SHA.

Native analysis кешируется по tenant + SHA + имени файла + `eis-native-v1`.
Имя существенно для определения формата. Кеш сохраняет полный результат
существующего bounded extractor: блоки, provenance, кандидаты требований и
условия. Перенос на новую версию требует нового получения файла и проверки
байтов; после этого тот же результат можно использовать повторно. Изменение
extractor/mapper/config требует новой версии analysis и отдельной миграции/
перестроения, а не перезаписи старого evidence.

Worker делает один сетевой шаг за запуск вне SQL-транзакции. При сохранении
байтов, анализа и observation используется общая атомарная транзакция с
tenant lock; извлечение bounded и не вызывает внешний LLM. GET читает только
сохранённые результаты. `DocumentAnalysis.status=PASS` относится к извлечению
текста; кандидаты не reviewed, роль документа и полнота остаются UNKNOWN.

Существующий downloader сохраняет host delay 60 секунд и проверку официальных
URL/TLS. API и worker используют один volume cooldown/lease. Серверный flock
исключает параллельный document/corpus/manual intake. Ошибка файла имеет
30-минутный cooldown; host-busy/delay — 60 секунд. Остановка proxy не создаёт
receipt или ложный COMPLETE.

## Последствия

Первый сбор комплекта занимает несколько минут с учётом ограничений источника.
Повторный просмотр не скачивает файлы и не запускает native extraction заново.
Поиск карточек сохраняет независимую скорость. Ограничения: 32 файла/100 МиБ
на notice, 20 МиБ на файл; DB guard 100 ГиБ и свободный резерв 40 ГиБ перед
сетевым шагом. Нет итогового допуска, утверждённых требований, LLM transfer,
КП или трёх сценариев экономики. Автоматический выбор top-N и полная проверка
комплекта остаются следующими этапами.

## Альтернативы

SQLite пилотного browser workflow не используется для этой очереди: серверный
индекс и RLS уже в PostgreSQL. Выполнение в запросе API удерживало бы клиента
на время сети/извлечения; повторное использование по URL/UID без SHA могло бы
перенести устаревшие байты. Mutable job status заменён проекцией immutable
наблюдений, чтобы сохранить историю и избежать ложного завершения после crash.

## Дополнение 28.09: пакетный подбор

Автоматический выбор top-N реализован отдельным операторским POST по запросу,
с лимитом 1..5. Последние известные XML сравниваются в snapshot S123;
карточки с FAIL и без приложений исключаются до применения лимита. Точный
список выбранных версий/SHA и конфликты записываются в tenant audit.
Повтор использует существующие задания; сеть выполняет прежний worker.
Выбор остаётся PRELIMINARY и не подтверждает допуск, прибыль или полноту ЕИС.
