# ADR 0008: серверный BFF для первого пилотного экрана

Дата: 2026-09-08. Статус: принято для S3.

## Контекст

S2 принимает bearer-ключ и определяет tenant на сервере. Передача этого ключа в
browser JavaScript, `localStorage` или публичную переменную Next.js нарушила бы
границу секретов. Полноценные пользовательские сессии, RBAC и MFA ещё не
реализованы, но первый внутренний экран нужен для проверки workflow кейса.

## Решение

Next.js App Router в первом пилоте работает как server-side BFF. Он читает
`PROCUREMENT_API_URL` и `PROCUREMENT_API_TOKEN` только в server modules, делает
запросы к FastAPI и отдаёт браузеру уже разрешённые данные. Формы импорта и
пересчёта выполняются на сервере и создают новый `Idempotency-Key` для каждой
осознанной команды пользователя.

Пилот конфигурируется для одного tenant. Цвет карточки берётся только из
persisted `Recommendation.decision`; рейтинг не может сделать карточку зелёной.
При отсутствии сохранённой оценки интерфейс показывает `UNKNOWN`/«требует
анализа» и предлагает пересчёт. Деморежим включается явной серверной настройкой
и заметно помечает все данные экрана.

## Последствия

Bearer secret не попадает в клиентский bundle и сетевые запросы браузера к
FastAPI. CORS для этого среза не требуется. Экран можно использовать для
внутренней проверки одного настроенного tenant, но нельзя выдавать за
production multi-user authentication.

Следующий auth-срез заменит общий серверный token на пользовательскую сессию с
RBAC/MFA и сохранит тот же BFF-контракт. Метрики мониторинга, заявок и контрактов
не имитируются до появления соответствующих событий и read models.

## Альтернативы

Хранить bearer в браузере — повышает риск утечки. Принимать token в форме входа
без server-side session — создаёт ложную модель безопасности. Показывать
синтетические метрики как реальные — нарушает объяснимость и доверие к экрану.
