# ADR-0022: OpenRouter для семантических кандидатов требований ТЗ

Дата: 2026-09-16  
Статус: принято для тестового среза

## Контекст

Детерминированный mapper S4 был построен как безопасный прототип нескольких
правил, но фактически стал основным путём анализа. На реальной приватной выборке
из 11 mapping units он покрыл один из 2 853 блоков. Особенно плохо обрабатываются
таблицы, где название характеристики, оператор, значение и единица находятся в
разных ячейках. Это не дефект чтения DOCX: native extraction получает текст и
точные locators, но регулярные выражения не дают общего понимания ТЗ.

Продуктовый инвариант остаётся прежним: LLM извлекает и предлагает структуру,
детерминированные правила и человек принимают решения. Нельзя напрямую превращать
непроверенный ответ модели в hard gate, completeness `PASS`, рекомендацию или
поиск/внешнее действие.

Для тестов выбрана доступная через OpenRouter модель
`google/gemma-4-31b-it:free`. Каталог OpenRouter заявляет для неё JSON
`response_format`, но не гарантирует strict JSON Schema enforcement. Поэтому
ответ провайдера сам по себе не считается типизированным evidence.

Live probe показал, что бесплатный Gemma endpoint не совместим с ZDR. Для
privacy-safe пилота также разрешён capability-profile
`inclusionai/ling-3.0-flash-vl:free`: он имеет бесплатный ZDR endpoint, но не
поддерживает `response_format`. Поэтому этот параметр для Ling не отправляется,
а JSON по-прежнему задаётся промптом и целиком проверяется локальной схемой.
Произвольный model slug не получает неявных capability-допущений: до добавления
явного профиля такой вызов отклоняется как `UNSUPPORTED_MODEL_PROFILE`.
Ling фактически возвращает валидный JSON внутри единственного fenced block.
Адаптер снимает только точную внешнюю ограду `json`; текст до/после, вложенная
ограда и любой невалидный JSON по-прежнему отклоняют chunk целиком.

Второй контракт извлечения использует отдельные версии
`ai-requirements-v2` / `ai-requirement-analysis-v2`; v1 остаётся неизменяемым и
валидируется отдельной веткой без silent upgrade. V2 отделяет
`AiProcurementItemCandidate` от требований. Наименование, каждый ОКПД2, каждый
КТРУ, единица и количество имеют собственные server-bound evidence blocks.
Количество принимается только строкой, преобразуется прямо в положительный
конечный `Decimal`; float, bool, неоднозначная запись и значения `<= 0`
отклоняются. Код подтверждается только синтаксически и обязан буквально
присутствовать в своём evidence; это не доказывает актуальность классификатора.
AI-позиция не преобразуется в доменный `LineItem` и не получает значений по
умолчанию.

## Решение

Добавляется `procurement.documents.ai_requirements` и явная CLI-команда
`analyze-tz-ai`. Внешнему провайдеру передаётся только текст полного native
extraction, разбитый на стабильные chunks. Строки DOCX- и XLSX-таблиц не
разделяются, а первая физическая строка таблицы повторяется как заголовок при
переходе к следующему chunk. Многострочные или расположенные ниже заголовки
остаются явным ограничением этого среза.

Модель возвращает только review-кандидаты:

- предполагаемые item/property/operator/value/unit и обязательность;
- идентификаторы фактически переданных source blocks;
- явную неопределённость, если значение нельзя установить.

Document ID, locator, исходный текст и provenance модель не назначает. Они
восстанавливаются приложением из неизменяемого `ExtractionResult`. Неизвестный
block ID, лишнее поле, повтор JSON-ключа, `NaN`, неверный тип, неподходящая форма
operator/value, timeout или provider error отклоняют весь chunk в `UNKNOWN`.
Кандидаты используют отдельную строгую схему и не являются доменными
`Requirement`; compliance их не читает.

Каждый отчёт связывает обязательный `company_id`, source SHA-256, extraction
SHA-256, model, prompt version, request/response digests, provider generation ID,
каждый chunk и точные evidence blocks. Даже полностью выполненный run имеет
`completeness_status=UNKNOWN/HUMAN_REVIEW_REQUIRED`.

Вызов OpenRouter разрешён только явно выбранной командой и требует непустой
`authorization_reference`. Ключ читается во время вызова только из
`OPENROUTER_API_KEY`, не является CLI-параметром, не входит в digest, модели,
отчёты или ошибки. Endpoint фиксирован на HTTPS, redirects и proxy environment
по умолчанию отключены. В среде, где прямой DNS/egress недоступен, системный
`HTTPS_PROXY`/`ALL_PROXY` разрешается только отдельным CLI-флагом
`--allow-env-proxy` и с явным указанием этого маршрута в authorization reference.
Proxy URL и credentials не сохраняются и не выводятся. Запрос по-прежнему требует
`data_collection=deny`, `zdr=true` и
`require_parameters=true`; OpenRouter документирует эти controls в
[provider routing](https://openrouter.ai/docs/guides/routing/provider-selection)
и [ZDR](https://openrouter.ai/docs/guides/features/zdr).

Первый срез ограничен одним полным native PDF/DOCX/XLSX за запуск. OCR,
embedded media, ZIP, persistence/API, независимый review и конвертация принятых
кандидатов в executable requirements являются следующими срезами. Существующий
regex mapper сохраняется как legacy deterministic extractor и regression oracle,
но не считается полноценным анализатором реальных ТЗ.

## Последствия

- Тестовый pipeline начинает использовать модель того же класса, который
  предполагается в production, вместо расширения бесконечного набора regex.
- Связанные ячейки таблиц попадают в один контекст, сохраняя точные citations.
- Бесплатный endpoint может быть недоступен при обязательных ZDR/data-policy
  ограничениях или rate limit; это остаётся `UNKNOWN`, без скрытого fallback на
  другую модель или менее безопасного провайдера.
- Передача текста ТЗ является внешней передачей данных и требует разрешения
  владельца; локальный extraction сам по себе такого разрешения не даёт.
- Нельзя подключать AI-кандидаты к sourcing или compliance до persisted review,
  нормализации единиц и доказанного полного покрытия.

## Отклонённые альтернативы

- Продолжать расширять regex как основной анализатор — отклонено: реальные
  таблицы и свободные формулировки требуют семантического контекста.
- Передавать ответ модели прямо в `Requirement` — отклонено: существующий
  compliance не защищён одной лишь LLM confidence.
- Разрешить модели возвращать собственные locator/document ID — отклонено:
  provenance обязан восстанавливаться из server-owned evidence.
- Ослабить privacy routing ради бесплатного endpoint — отклонено: отсутствие
  подходящего безопасного route должно быть видимым `UNKNOWN`.
- Скрыто переключаться на другую модель при ошибке — отклонено: результат нельзя
  воспроизвести и связать с заявленной моделью.
