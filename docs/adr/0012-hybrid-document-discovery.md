# ADR 0012: гибридный поиск по нативному тексту и vision-тегам

Дата: 2026-09-15. Статус: принято для S4.

## Контекст

Для первичного отбора подрядчику достаточно находить закупочные документы по
названию, имени файла и текстовой части ТЗ: например, «ремонт этажа»,
«выполнение работ» или «кондиционирование». Полное построчное OCR чертежа для
этого сценария избыточно: пользователь откроет найденный DOCX и изучит чертёж
самостоятельно. При этом короткие надписи и коды оборудования на чертеже могут
быть полезны как дополнительные поисковые признаки.

На проверенном реальном DOCX нативный текст уже содержит описание ремонта
системы кондиционирования, а имя файла — слова «ремонт», «кондиционеров» и
«этажа». На связанном изображении визуально подтверждены «Кондиционирование»,
«Наружный блок» и коды моделей. Название `General Climate` не найдено ни в
нативном тексте, ни на изображении, поэтому вывести бренд из кода модели без
отдельного каталожного источника нельзя.

## Решение

- Индексировать название процедуры, исходное имя файла и каждый нативно
  извлечённый блок отдельно, сохраняя источник совпадения и provenance.
- Разрешить поиск по полезным нативным блокам, даже когда общий результат
  извлечения документа остаётся `UNKNOWN/EMBEDDED_MEDIA_IGNORED`. Это не снимает
  неполноту документа и не влияет на compliance.
- Хранить короткие vision-теги отдельным versioned manifest, связанным с точными
  SHA-256 DOCX, реально связанного DOCX media, prompt и исходного review artifact.
  Перед поиском повторно раскрывать DOCX relationship и сверять media index,
  archive path и digest.
- AI-тег даёт только discovery-совпадение `UNKNOWN`; подтверждённый человеком тег
  может дать `PASS` только для поиска. Ни один vision-тег не становится
  требованием, hard gate или основанием участия.
- Не индексировать автоматически сырой OCR и его кандидаты. Для vision разрешены
  только краткие признаки, явно видимые на изображении; внешний документ
  считается недоверенным вводом и не меняет policy.
- Для русских форм использовать ограниченное детерминированное сопоставление:
  нормализацию регистра/`ё`, подстроку и общий кириллический префикс длиной не
  менее семи символов. Полноценные синонимы, морфология и ранжирование остаются
  отдельным поисковым срезом.

## Последствия

Текущий локальный CLI находит реальный DOCX по «ремонт», «выполнение работ» и
«кондиционирование». Запрос к коду `GW-G140W/N1D3` возвращает только AI vision
evidence со статусом `UNKNOWN`. Запрос `General` не возвращает совпадений;
поддержка такого запроса потребует доказательного каталога соответствий
`model → brand`, а не догадки модели.

Срез является локальным in-memory proof: search entries и vision manifests ещё
не сохраняются в PostgreSQL и не доступны через tenant API. Production-версия
потребует аутентифицированного review, immutable persistence, audit и
полнотекстового/семантического индекса. Внешняя vision API в этом решении не
вызывается и по-прежнему требует exact-payload approval и принятой retention
policy.

## Альтернативы

Полное OCR всех чертежей создаёт много ошибок и расходует ресурсы на текст,
который не нужен для первичного поиска. Игнорирование изображений полностью
теряет полезные обозначения и модели. Смешивание AI-тегов с нативным текстом
скрывает разницу в доверии. Выбран раздельный гибридный индекс с явным статусом
каждого совпадения.
