# ADR 0006: проверяемый кейс до внешней автоматизации

Дата: 2026-09-07. Статус: принято.

## Контекст

Исходная библиотека принимает счётчик КП и безымянные статусы от вызывающего кода.
Такая граница не доказывает, что проверен именно текущий профиль, текущая процедура
и действующее предложение. Нулевые значения расходов и предполагаемая ставка НДС
могут скрывать отсутствие входных данных. Пользователь поручил начать
последовательную разработку с разделением задач между моделями.

## Решение

Первый срез принимает типизированный, вручную проверенный ProcurementCase.
Он содержит выбранное КП, обязательные именованные проверки и сценарии;
оценка связывается с точным снимком входных данных. Полнота расходов сохраняется
при сериализации отдельно от предварительных нулей. Неизвестная ставка НДС
блокирует положительное решение.

Основной публичный путь решения проверяет актуальность и согласованность кейса.
Старые скалярные аргументы не являются достаточным основанием участия.
CLI для локального JSON импорта создаёт воспроизводимый результат без внешних
действий. В S1 одна валюта RUB и одно КП на весь комплект поставки.

## Последствия

Можно проверить финансовые и доказательные ограничения до создания UI и
подключения ЕИС. Положительный результат по ручным проверкам не означает,
что реализован автоматический юридический анализ. Хеш — связь снимков, не
аутентификация проверяющего; доверие и audit storage появятся в S2.

Старые вызовы recommendation и fixtures адаптируются к новой границе. Реальные
отправки, одноразовое исполнение approvals, переменные налоги и multi-supplier
расчёт требуют следующих срезов. Правовые запреты не меняются этим ADR.

## Альтернативы

Сначала UI над старой функцией — сохраняет возможность ложной зелёной карточки.
Сразу весь мониторинг и автоподача — увеличивает число непроверенных зависимостей.
Полностью переписать библиотеку — теряет уже проверенные compliance-инварианты.
