# ADR 0013: неизменяемые версии tenant-scoped поискового индекса

Дата: 2026-09-15. Статус: принято для S4.

## Контекст

ADR-0012 разделил нативные поисковые признаки и vision-теги, но первый вариант
работал только локально в памяти. Для API-поиска необходимо сохранять точную
версию поискового evidence, не терять связь с исходным документом и не позволять
одному tenant увидеть индекс или результат другого.

Название процедуры и human review могут появиться позже загрузки документа.
Обновление одной строки на месте уничтожило бы предыдущую доказательную версию.
Хранение только нормализованной строки также потеряло бы блоки, locators и
различие доверия между native и vision sources.

## Решение

- Хранить каждую версию как append-only `document_search_indexes` с tenant,
  собственным ID, FK на исходный документ, SHA-256 документа, полным typed
  `DocumentSearchEntry` JSON и timezone-aware временем.
- Перед записью внутри одной tenant-scoped транзакции повторно читать immutable
  document bytes/extraction и полностью перестраивать entry. Для vision повторно
  проверяются DOCX relationship, media index/path и SHA-256.
- Запись индекса, audit event `document.search_index_stored` и idempotency receipt
  выполнять атомарно. Повтор exact request возвращает прежнюю версию; другой
  payload с тем же ключом конфликтует.
- Поиск выполняется только по последней версии каждого документа, которую может
  прочитать текущий tenant. Результат сохраняет status и provenance каждого hit.
- RLS/FORCE RLS и права таблицы разрешают приложению только `SELECT, INSERT`;
  trigger запрещает `UPDATE` и `DELETE`.
- В этом срезе Python фильтрует ограниченный набор последних typed entries.
  Специализированный полнотекстовый индекс и ранжирование добавляются после
  подтверждения поисковой семантики на реальном наборе.

## Последствия

API предоставляет создание версии `POST
/v1/documents/{document_id}/search-indexes` и tenant-scoped поиск `GET
/v1/document-search?query=...`. Исходные bytes в ответ не входят. Отсутствующий и
чужой документ одинаково дают `404`; результат другого tenant не возвращается.

Версионирование позволяет позже добавить подтверждённые vision-теги или изменить
название без мутации старого evidence. Цена текущего простого решения — загрузка
ограниченного набора JSON entries и поиск в Python; это не production-scale
полнотекстовый движок.

## Альтернативы

Изменяемая строка на документ проще, но нарушает воспроизводимость. Поиск прямо по
`documents.extraction` не хранит title/vision evidence как отдельную версию.
Смешивание нормализованного текста в одной колонке теряет provenance. Внешний
поисковый сервис преждевременен до проверки качества и потребовал бы отдельной
tenant/security модели.
