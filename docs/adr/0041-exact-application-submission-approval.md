# ADR-0041: краткосрочное подтверждение exact команды подачи

Дата: 2026-09-21  
Статус: Accepted for the local pilot

## Контекст

S94 подтверждает полноту и цену immutable комплекта, но не фиксирует адрес
подачи и не даёт разрешения на внешнее действие. Подача юридически значима:
изменение цены, файла или адреса после review должно делать подтверждение
непригодным. Слой подписи и адаптер площадки пока отсутствуют.

## Решение

Оператор создаёт один `application-submission-intent-v1` для пакета с terminal
`PASS` review. Сервер заново вычисляет `PARTICIPATE`, deadline и актуальный
ценовой коридор; проверяет HTTPS адрес и строит канонический `ActionRequest`
типа `SUBMIT_APPLICATION`. Его payload включает точный адрес, case/version,
package/review SHA-256, Decimal-цену строкой, валюту и упорядоченный перечень
каждого файла: ID, SHA-256, имя подачи и MIME type. Клиент не может заменить
цену или состав файлов в POST. Один пакет получает не более одной команды.

Независимый `APPLICATION_SUBMISSION_APPROVER` сверяет показанный payload и
указывает `APPROVED | REJECTED` с основанием. Его actor ID должен отличаться
от автора пакета, проверяющего пакет и автора команды. Положительное решение
даёт `Approval` только для exact action ID и payload SHA-256 на 15 минут, но не
дольше deadline и срока действия выбранного КП. При решении сервер снова
проверяет актуальные гейты.
Отрицательное решение terminal и не имеет `Approval`. Решение, intent и
связанные audit events/receipts сохраняются атомарно в tenant-scoped
append-only таблицах с RLS/FORCE RLS, composite FK и проверкой JSON identity.
Чтение реконструирует оба объекта из S93/S94 evidence.

Operator BFF и отдельный approver BFF используют разные server-only tokens.
Экран согласующего показывает весь exact payload и его SHA-256. Роль AUDITOR
имеет только чтение. Подготовка и согласование не подписывают и не отправляют
заявку; `external_action_performed=false`.

## Последствия

Это подтверждение фиксирует внутреннюю команду, а не произвольное тело запроса
конкретной площадки. Будущий исполнитель обязан в одной транзакции проверить
неизменность команды и реальных файлов, актуальные deadline/floor/участие,
срок `Approval` и его одноразовое потребление. Если адаптер преобразует
команду в отличающийся platform wire payload, потребуется отдельное
подтверждение точных байтов после такого преобразования. Доменная функция
`submission_approval_is_current` — только чистая проверка и сама по себе не
является допуском к отправке. Локальный BFF различает роли по server-only API
keys, но сам не удостоверяет личность посетителя страниц; независимость сейчас
обеспечена на уровне actor ID ключей. Перед производственной подачей нужны
персональная аутентификация согласующего с MFA, контроль доступа к approver
route и доверенный реестр адресов площадок.
