# ADR-0043: проверяемый архив для ручной передачи заявки

Дата: 2026-09-21  
Статус: Accepted for the local pilot

## Контекст

После S96 сервер умеет подготовить и проверить exact команду, но конкретная
ЭТП, разрешённый способ интеграции, wire format, юридическая проверка,
персональная MFA и доверенный allowlist ещё не заданы. Реальную автоматическую
подачу и квитанцию площадки реализовать без этих данных нельзя. Оператору при
этом нужен единый проверяемый набор оригиналов для ручной работы.

## Решение

Добавить read-only `application-handoff-v1` ZIP на отдельном маршруте роли
`APPLICATION_SUBMISSION_EXECUTOR`. Сборка требует действующий exact approval и
повторно проверяет deadline, `PARTICIPATE`, ценовой floor и байты всех
`APPLICATION_ATTACHMENT`. Сервер сверяет tenant, роль, MIME и SHA-256 каждого
документа. Архив содержит `manifest.json` с package/action/approval digest,
адресом, ценой без НДС, сроком approval и упорядоченным перечнем файлов; SHA-256
манифеста считается по каноническому JSON. Файлы лежат под безопасными именами
`files/<ordinal>-<submission_filename>`. Общий размер ограничен 100 MiB.

Маршрут отклоняет запрос после существующего admission и не предоставляет
архив при истёкшем approval или изменённых оригиналах. BFF использует
server-only executor token и отдаёт ZIP с `no-store`/`nosniff`. Архив не
передаётся на площадку автоматически.

## Последствия

`external_action_performed=false`: скачивание не является подачей, подписью
или квитанцией. Ручное действие и его результат остаются вне системы. Проверка
отсутствия admission при GET не является атомарным claim и не исключает гонку
с параллельным admission. До добавления автоматического dispatch потребуется
разделить эти ветви атомарно, зафиксировать результат ручной подачи и получить
новое exact approval на platform wire payload. Архив может быть собран повторно
только пока действуют те же approval и gates.
