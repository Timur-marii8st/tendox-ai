1. Как работает сейчас (Этап 0)

Сейчас это библиотека, а не сервис. Нет сети, нет базы, нет LLM, нет UI. Единственный способ запуска — из Python или из тестов. Это сделано намеренно: методика проверки соответствия зафиксирована в коде и тестах прежде, чем вокруг неё появится инфраструктура, которую потом дорого переделывать.

2. Как будет работать (MVP → v1)

Главный принцип схемы: LLM извлекает, правила решают. Языковая модель превращает документы в структуру и предлагает сопоставления; вердикт выдаёт тот самый детерминированный движок, который уже написан. Из этого следует практический вывод для железа: ошибка модели стоит уточняющего вопроса, а не неверного вердикта, поэтому требования к «уму» модели заметно ниже, чем у систем, где LLM решает сама.

3. Вариант A: LLM по API

Своих GPU нет вообще. Сервер занят только приложением, базой, очередями и разбором документов. Это правильный вариант для MVP: он даёт лучшие модели за нулевые капитальные затраты и позволяет померить реальный профиль нагрузки, прежде чем покупать железо.

Формула месячного счёта: ТЗ_в_месяц × (вход × цена_входа + выход × цена_выхода). 4. Вариант B: свои модели на своём железе

Причина переходить на локальный инференс здесь не в цене, а в данных: ТЗ и КП — это коммерческая тайна заказчика и персональные данные контактных лиц. Часть клиентов (особенно с гостайной, ГОЗ или требованиями ФСТЭК в контуре) не подпишет договор, в котором их ТЗ уходит во внешний API. Локальные модели — это функция продаж, и только во вторую очередь экономия.

Сколько нужно VRAM: как считать

Память под модель складывается из трёх частей:

VRAM ≈ вес модели + KV-кэш + накладные расходы (10–15%)

  • Вес модели = число параметров × байт на параметр: FP16 — 2, FP8/INT8 — 1, INT4/AWQ — примерно 0,55 с учётом масштабов квантования.
  • KV-кэш растёт линейно от длины контекста и от числа одновременных запросов. Именно он, а не вес модели, определяет реальный потолок.
МодельВес FP16Вес FP8Вес INT4KV-кэш на 1k токенов (FP16)KV на 128k контекста
8B16 ГБ8 ГБ≈ 4,5 ГБ≈ 0,13 ГБ≈ 17 ГБ
14B28 ГБ14 ГБ≈ 8 ГБ≈ 0,16 ГБ≈ 21 ГБ
32B64 ГБ32 ГБ≈ 18 ГБ≈ 0,26 ГБ≈ 33 ГБ
70B140 ГБ70 ГБ≈ 39 ГБ≈ 0,33 ГБ≈ 42 ГБ
Главный вывод для нашей задачи: ТЗ на 60 страниц — это 60–150 тысяч токенов контекста. На длинных документах KV-кэш сопоставим с весом самой модели или больше его. Поэтому «32B влезает в 24 ГБ в INT4» — правда только для коротких промптов и бесполезна для разбора ТЗ. Считать надо всегда вместе с контекстом, и кэш стоит держать в FP8 — это уменьшает его вдвое почти без потери качества.

5. Сравнение и порядок действий

КритерийLLM по APIСвои модели локально
Капитальные затратынулевыеот рабочей станции до серверного узла в ЦОД
Постоянные затратырастут пропорционально числу ТЗпочти постоянные: электричество, стойка, инженер
Качество на длинных документахвыше — доступны сильнейшие моделиниже, но для «извлечь и предложить» этого достаточно
Данные клиентауходят внешнему провайдеру, нужен договор и проверка резидентностине покидают контур — снимает возражение на продаже
Время до результатаднинедели-месяцы: закупка, монтаж, настройка, калибровка
Рисксмена тарифа или отключение доступаденьги вложены в железо, которое дешевеет

Экономика перехода считается просто: месячный счёт за API против амортизация железа + электричество + стойка + зарплата инженера. Своё железо начинает выигрывать только при устойчиво высокой и предсказуемой нагрузке — а её на Этапе 0 ещё нет, потому что нет ни одного реального ТЗ, прошедшего через систему.

Рекомендуемый порядок:
  1. MVP — только API. Замерить реальные токены на ТЗ и долю сканов в документах.
  2. Появился клиент с запретом на внешний API — арендовать GPU в российском облаке и собрать конфигурацию Т2. Аренда, а не покупка: она отвечает на вопрос «какая модель нам достаточна» без капитальных затрат.
  3. Покупать железо тогда, когда счёт за API или аренду стабильно превышает амортизацию своего узла, либо когда локальный контур становится условием сделки.
Что здесь требует проверки. Цифры VRAM и KV-кэша расчётные — их надо подтвердить замерами на выбранной модели и на реальных ТЗ. Тарифы API, стоимость аренды GPU в РФ и цены на карты в документ не внесены сознательно: по правилам проекта непроверенный факт не может быть основанием архитектурного решения, см. docs/07-research-log.md.
