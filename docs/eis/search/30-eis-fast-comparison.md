# Быстрый поиск и сравнение актуальных версий ЕИС

Дата: 2026-09-28. Архитектура: [ADR 0046](../../adr/0046-eis-lexical-prefilter.md).

Уточнение S134, 01.10: query prefilter и comparator исключают служебные
`для/при/или/как/это/что` через `search_query_keys_v1`. Иначе «для» возвращало
посторонние товары и расширяло query до десятков тысяч карточек. Persisted
`search_keys_v1` и title/item ключи неизменны; reindex не требуется. Запрос
только из служебных слов невалиден. Методика и before/after baseline:
[34-eis-search-benchmark.md](34-eis-search-benchmark.md).

## Что реализовано

1. При атомарном импорте XML сохраняются version-bound поисковые ключи.
2. PostgreSQL выбирает подходящие заголовки/позиции и исключает версии,
   заменённые более новыми. Карточки без ключей остаются в обычном поиске.
3. Все выбранные кандидаты сравниваются детерминированным движком; только
   затем возвращаются первые 100. Полное совпадение требует одного поля,
   подтверждённая отмена и истёкший срок блокируют кандидата.
4. Один read-only snapshot связывает статистику, XML и события. В ответе
   сохраняются SHA, версии, ссылки, локаторы и объяснения.
5. Интерфейс показывает число карточек, реально сравненных кандидатов и время
   серверного поиска. Последний импорт и известная публикация показаны отдельно.

`source_freshness=UNKNOWN` и `comparison_kind=PRELIMINARY`. Последняя публикация
в загруженном наборе не доказывает, что источник больше не менялся. Действующий
deadline сам по себе не подтверждает открытый этап подачи.

## Проверка

На основном VPS, в отдельной удаляемой PostgreSQL БД: 50 000 синтетических
карточек, запрос «серверное оборудование», 49 совпадений. Обычный разбор без
ключей: 6724 мс; после backfill: 54, 50, 49, 49, 49 мс. Содержимое результатов
совпало полностью. Подробно разобрано 49 вместо 49 999 строк без ключей.
Это измерение узкого запроса без большой очереди синхронизации и без скачивания
документов; оно не является SLA для любых запросов или всей ЕИС.

11 PostgreSQL gates проверили миграцию, tenant isolation, immutable keys,
fallback/replay/backfill, последние версии, отдельные позиции, deadline,
отмены и согласованное чтение при параллельном импорте. Unit/API tests,
Ruff, strict mypy и production web build также прошли. Перед production
миграцией создан backup. Результат live API/UI фиксируется в основном плане.

Live API с очередью 144540 targets: серверное оборудование — 203 кандидата
из 2765 последних известных карточек за 309 мс; бумага — 51 за 142 мс.
Сквозной браузерный поиск показал 51 карточку, счётчики и UNKNOWN свежести.
Последняя известная публикация корпуса: 2026-09-27 19:22:47.326 UTC;
сегодняшняя полнота обновлений не подтверждена из-за недоступности proxy VPS.

Миграция `20260928_03` создаёт новую таблицу, не меняя исходные версии. Для
пилотной компании проиндексированы все 2918 версий. Для другого tenant старый
корпус перестраивается отдельно:

```bash
cd /home/syurai/vibe-seller
sudo -n docker compose -f docker-compose.server.yml run --rm --no-deps \
  -v /home/syurai/vibe-seller/scripts:/app/scripts:ro worker \

```

Повтор не добавляет дубли. Новый импорт получает ключи автоматически. Разбор
идёт по 500 версий за транзакцию; progress отражается в tenant audit. Исходные
XML и архивы не удаляются. Benchmark жёстко использует только отдельную БД
`procurement_eis_test_20260928`; запуск в production не допускается скриптом.

## Что требуется для полного сравнения выгодности

Следующий порядок сохраняется:

1. Восстановить доступ к официальному источнику; проверить регионы/типы и
   закрыть gaps. Для свежести нужны регулярные обновления, включая изменения
   сегодня и текущие этапы/отмены, а не только завершённые даты.
2. В фоне собирать комплект документов кандидата, считать SHA и version-bound
   результаты извлечения требований. При изменении XML/файла повторять только
   изменившийся анализ; неполный комплект остаётся UNKNOWN.
3. Связать позиции с реально сопоставимыми действующими полными КП; считать
   все расходы через Decimal и base/realistic/conservative сценарии.
4. Применять hard gates; добавить доказуемые результаты прошлых процедур и
   конкуренцию, затем объяснять порядок по выгоде и рискам.

ИИ извлекает и сопоставляет данные; допуск и экономика проверяются правилами.
Мгновенный повторный просмотр возможен по подготовленному анализу, а первый
разбор новых PDF/DOCX/сканов выполняется очередью и имеет видимый статус.
Широкие запросы с очень большим числом совпадений требуют следующего
оптимизационного среза; лимит ответа не скрывает стоимость полного сравнения.

## Локальное уточнение смысла «бумага» — 09.10.2026

Статус: local verified, **не установлен**. Общий comparer 44/223 не засчитывает
бумажный term по соседней финансовой фразе «ценные бумаги», если query сам
не содержит явную форму прилагательного «ценный». Формы прилагательного
проверяются отдельно от stem: «цены бумаги»/«цен бумаги» остаются обычным
paper evidence. Другие вхождения бумаги в том же поле/позициях сохраняются.
Явный финансовый запрос продолжает находить финансовые услуги. Это ограниченное
контекстное правило; общий stemmer, ranking, hard gates и persisted v1 keys
