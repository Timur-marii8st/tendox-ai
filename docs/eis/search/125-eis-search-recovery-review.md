## Почему продвижение не превращалось в готовый поиск

1. Восстановление отдельных архивов измерялось успешно, но не закрывало acceptance
   пользователя: присутствует ли конкретная действующая закупка в выдаче.
   Большой historical pending смешивает историю, NO_DATA и разные координаты;
   он не даёт ни процента полноты, ни срока готовности актуального поиска.
2. Текущий режим hourly44 в проверенном интервале не успевает за450 окнами/час,
   дополнительно обслуживая223, reconciliation и историю. Поддержка новых типов
   увеличит нагрузку. Повышение cron frequency при общем lease/budget этого не решает.
3. Поиск цены перебирает все matching leads обоих законов в Python до выбора
   страницы; регион вызывает navigation/source reads по кандидатам. Это связывает
   время ответа с объёмом корпуса. Загрузка новых данных сама по себе его не ускорит.
4. Дисковый резерв уже останавливает ingestion. Рост хранилища без retention/capacity
   работы будет снова останавливать данные. Нельзя удалять audit/backup/архивы вслепую.
5. Полнота поддержанных типов не означает полноту ЕИС. Требуется разбор пропусков
   по семействам и независимым номерам, а не обещание «докачать всю ЕИС».

## Предлагаемый порядок и архитектура

Ближайший продуктовый результат: сверяемая выдача действующих закупок бумаги
с сопоставимыми фильтрами и объяснением каждого известного пропуска.
Первое следующее действие — получить фиксированную контрольную выдачу ЕИС по
«бумага» и сопоставить номера/версии/стадию/регион/цену с установленным поиском.
Использовать существующие capture/benchmark и by-number tools. Внешняя страница
через web tool в этом срезе недоступна; captured ground truth отсутствует, recall UNKNOWN.
Сначала разобрать самые дорогие релевантные закупки, а не очередные случайные архивы.

Далее последовательные срезы; каждый заканчивается измеренным пользовательским
результатом, а не подготовкой очередного helper:

1. По установленной причине закрыть контрольные пропуски и разделить в выдаче
   предмет закупки/лот и совпадение внутри состава или документа. Сохранить поиск
   по ТЗ; не объявлять весь бюджет смешанного лота ценой искомой бумаги.
2. Вынести цену Decimal, валюту/вид цены, регион поставки, срок, статус, версии,
   holds и поля совпадений в проверенную поисковую проекцию при ingestion.
   Provenance и SHA связывают каждое поле с raw; cancellation/hold invalidation
   обязательны. SQL фильтрует и сортирует до LIMIT; API не разбирает архивы всех
   совпадений. PostgreSQL остаётся достаточной исходной платформой; смена стека
   без benchmark не является решением. Миграция/read model требует отдельного ADR.
3. Выбрать частоту обновления по измеренной мощности: гарантированная сверка
   завершённых дней, ограниченная текущая дельта, история на остатке. Не обещать
   национальный hourly SLA при observed throughput ниже arrival. Неподдержанные
   families приоритизировать по действующим контрольным пропускам. Контрольные
   повторные проверки NO_DATA и отмены сохранить; старые receipts не переписывать.
4. Одновременно с проектированием следующего release рассчитать запас диска и
   безопасное хранение evidence/backup. Подключение лицензированного поставщика
   данных рассмотреть как ускоритель, если собственный канал не закрывает нужные
   типы/свежесть: сначала тот же контрольный набор, права, версии/отмены и цена.
   Вендор, договор, бюджет и полнота такого источника пока не проверены.

Предлагаемые критерии приёмки: контрольные пропуски устранены; отдельные recall
и precision по фиксированному набору с одинаковыми фильтрами; целевой p95 поиска
≤5s на заранее согласованной нагрузке, без OOM; минимум24h наблюдения свежести,
скорость обязательной работы выше её поступления, latency/coverage отдельно по
44/223 и семействам. Эти цели не измерены и не объявлены PASS. Полнота истории
не блокирует полезный текущий поиск; релевантные активные закупки из старых дат
должны попадать в контрольный набор и восстанавливаться отдельно.
