## Цель и точный смысл охвата

Поставщик задаёт товар и профиль компании. Система ищет среди **фактически
синхронизированных публичных извещений** ЕИС, показывает подходящие действующие
процедуры, читает документацию отобранных кандидатов и объясняет порядок.
«Самые выгодные» означает сравнение проверенной экономики для поставщика, а
не сортировку по НМЦК, совпадению слов или цене прошлых контрактов.

Охват указывается как конкретные закон, виды процедур, статусы, период,
источник, время последней успешной синхронизации и известные пропуски.
Фраза «все закупки ЕИС» допустима только в подтверждённой границе источника
после сверки полноты. Закрытые и недоступные процедуры исключаются и не
считаются пропуском публичного корпуса. Если источник не даёт проверяемой
полноты, интерфейс показывает `PARTIAL/UNKNOWN`, даже когда импорт технически
завершён. Неуспешный поиск и отсутствие подходящих закупок различаются.

Индексируются карточки всего подтверждённого публичного корпуса в выбранной
границе. Подробные карточки и файлы скачиваются для ограниченного списка
релевантных кандидатов по очереди; лимит и непроверенные кандидаты видны.
Это позволяет расширять поиск без утверждения, что документация всех закупок
полностью разобрана.

## Последовательность и правила перехода

Каждый S-срез имеет одного владельца; перечисленные файлы — **предлагаемые
owned files будущей реализации**, а не утверждение об их существовании.
Следующий срез открывается после выполнения acceptance предыдущего. Нельзя
закрыть блокирующий гейт рейтингом. Все новые persisted-записи, задания и
audit events tenant-scoped; raw bytes, версии парсера, SHA-256, URL и локатор
сохраняются вместе с извлечёнными фактами. Денежные суммы — `Decimal`, deadline
— timezone-aware, внешние документы — недоверенный ввод.

### S123 — поиск по всему индексу и объяснимый первичный отбор

- **Владелец:** Terra. **Зависимости:** S121; S122 расширяет тот же поиск.
- **Owned files:** новые `src/procurement/sources/eis_index_search.py`,
  `tests/test_eis_index_search.py`, API поиска и
  `web/src/app/tender-discovery/` в этом последовательном срезе.
- **Работа:** точные фильтры закона, процедуры, статуса подачи, срока,
  региона, суммы, ОКПД2/КТРУ и характеристик; нормализация названий,
  синонимы и семантический поиск. Сначала извлекать широкий набор из всего
  индекса, затем детерминированно переупорядочивать. Для каждой карточки
  показывать совпавшие поля и причины исключения. `PUBLISHED` само по себе
  не означает открытую подачу; закрытый/истёкший срок блокирует кандидата.
- **Acceptance:** запрос не ограничен первыми страницами HTML ЕИС;
  пагинация собственного индекса стабильна при одинаковом snapshot/watermark.
  На заранее размеченном наборе запросов для бумаги, серверов и других
  категорий измерены recall@50 и ложные совпадения; целевой recall@50 ≥ 95%
  для подтверждённо релевантных активных карточек в пределах корпуса.
  Нельзя скрыть кандидата без причины или показать `PASS` из одного слова.
- **Проверка:** golden set, сравнение с независимой ручной выборкой ЕИС,
  нагрузочный тест поиска и tenant isolation.

**Частичный результат S123:** `eis_index_search.py` сравнивает все карточки
переданного архива без зависимости от пользовательского фильтра на этапе
загрузки, берёт последнюю версию номера, разделяет полное и частичное
лексическое совпадение по названию извещения или одной структурированной
позиции лота и объясняет выбор XML SHA/локатором. Слова из разных позиций
не складываются в ложное полное совпадение. Сценарная
оценка допускается только при расходах, привязанных к точному XML SHA;
частичное совпадение её не получает. На шести живых карточках «бумага»
дала одно полное совпадение, «медицинские маски» — одно полное и два частичных,
«серверное оборудование» — ноль в **этом окне**. Без КП выгода `UNKNOWN`.
Это ещё не SQL-поиск по PostgreSQL, не измеренный recall и не весь ЕИС.

**Срез формы XML/ZIP, 2026-09-27:** владелец — основной Codex;
owned files — `src/procurement/sources/eis_discovery.py`,
`tests/test_eis_discovery.py`, `web/src/lib/procurement-api.ts`,
`web/src/app/tender-discovery/form.tsx` и этот план. Форма теперь ищет
совпадение в названии извещения или **одной** позиции `purchaseObject` и
показывает `STRONG | PARTIAL` с XML-локатором. На живом ZIP запрос
«маска лицевая» нашёл одну карточку по второй позиции лота, запрос
«бумага офисная» — одну по заголовку, «серверное оборудование» — ноль
в данном часовом окне. Проверка: профильные тесты, Ruff, strict mypy;
полный результат остаётся предварительным без доказанного охвата корпуса.

### S124 — скачать и проверить комплект документов кандидатов

- **Владелец:** Sol. **Зависимости:** S123 и существующий document pipeline.
- **Owned files:** новый `src/procurement/sources/eis_document_sync.py`,
  новые профильные тесты; интеграция с `src/procurement/documents/` и API
  выполняется в этом срезе.
- **Работа:** для top-N релевантных карточек читать официальные ссылки и
  manifest файлов, скачивать с лимитами, сохранять immutable bytes/SHA-256,
  безопасно извлекать PDF/DOCX/XLSX/ZIP/XML и привязывать каждый факт к
  версии извещения и месту в документе. Проверять комплектность,

скачивание top-N ещё не готово. Экран показывает количество текущих карточек,

Продолжение 28.09: [очередь документов](../../documents/31-eis-document-queue.md) подключена

доходности. Проверены 16 PG integration tests, 72 профильных unit/API tests,
production build, интерфейс и восстановление резервной копии очереди.

### S125 — сравнить выгоду для конкретного поставщика

- **Владелец:** Sol. **Зависимости:** S124, профиль компании, проверенное
  действительное полное КП и существующие hard gates/economics.
- **Owned files:** `src/procurement/domain/discovery_economics.py`, новый
  слой привязки КП к лоту, профильные тесты и экран сравнения
  `web/src/app/tender-discovery/` в этом последовательном срезе.
- **Работа:** связывать точный состав лота с товаром/КП поставщика,
  количеством и условиями. Подключить существующий поиск производителей и
  предложений как источник кандидатов цены; карточка товара без срока,
  наличия и подтверждения всего лота остаётся гипотезой. Если нужен RFQ,
  исходящее сообщение проходит exact-payload approval, а ответ привязывается
  к версии лота и сроку КП. Считать доставку по адресам, налоги,
  обеспечения, финансирование, резервы и сценарии `base`, `realistic`,
  `conservative`. Показывать маржу, минимальную допустимую цену и основания.
  Сортировать по консервативной прибыли **только** кандидатов с сопоставимым
  полным расчётом; остальные — отдельная очередь `NEEDS_ANALYSIS`.
- **Acceptance:** неуказанная стоимость не равна нулю; изменившееся КП,
  лот или ТЗ требует пересчёта. Mandatory `FAIL` блокирует; `PARTICIPATE`
  возможно лишь после полного действительного КП, трёх сценариев и всех
  обязательных проверок. НМЦК без затрат не маркируется как прибыль.
- **Проверка:** сквозные тесты для бумаги и серверного оборудования,
  Decimal/НДС, нескольких адресов, истёкшего КП и отрицательной маржи.

### S126 — осторожная оценка конкуренции

- **Владелец:** Sol; high-risk review Astra. **Зависимости:** S122,
  официальные протоколы и результаты сопоставимых процедур.
- **Owned files:** новый `src/procurement/sources/eis_protocols.py`,
  `src/procurement/domain/competition.py` и профильные тесты.
- **Работа:** связывать извещение, лот, протокол и контракт по официальным
  ключам; учитывать регион, период, объём, предмет и способ закупки.
  Показывать диапазон фактического снижения, размер и качество выборки.
  Поправки и изменение цены контракта не трактовать как ставки участников.
- **Acceptance:** при неоднозначной связи или малой выборке результат
  `UNKNOWN`; нет процента «вероятности победы» без отдельной калибровки на
  отложенной выборке. Риск конкуренции не перекрывает hard gates и не
  подменяет расчёт прибыли.
- **Проверка:** реальные связанные и несвязанные пары документов,
  отрицательные тесты на ложную скидку и отчёт о качестве сопоставления.

### S127 — доказать покрытие и запустить регулярную работу

- **Владелец:** Astra (приёмка архитектуры и критериев); реализация
  операционных задач назначается отдельными непересекающимися slice.
  **Зависимости:** S120–S126.
- **Owned files:** новый runbook `docs/operations/27-eis-index-operations.md`,
  integration/e2e tests, экран качества источника и статус в
  `docs/15-implementation-plan.md`.
- **Работа:** расписание sync, мониторинг лага, ошибок, квот, изменения схем,
  восстановления после сбоя и стоимости хранения. Оператор видит границу
  корпуса и дату каждого вывода; старые оценки инвалидируются при новой
  версии источника или КП. Сверять полноту с официальными счётчиками/
  манифестами, когда они доступны.
- **Acceptance:** повторяемый запуск на разрешённой реальной выборке,
  проверенная изоляция компаний, восстановление после сбоя без пропусков,
  тесты ложного `PASS`, сохранённые evidence метрик. Только подтверждённые
  границы получают метку полного охвата; любые пробелы отображаются.
- **Проверка:** независимый пилот по двум товарным запросам, сравнение
  результатов с ручным эталоном, нагрузка, security review и журнал
  расхождений.
