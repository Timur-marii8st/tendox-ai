Тесты S129 страницы 21 считали HTTP/карточки без проверки уникальности;

[аудит стратегии](../../research/32-eis-data-strategy-review.md).

## Контракт

Вход — товарный запрос поставщика. Живой путь `GET /v1/tender-discovery/eis-live`
читает первую страницу публичного поиска ЕИС штатным Chromium с фильтром
«Подача заявок», 44-ФЗ и 223-ФЗ. Из до 100 карточек отбираются совпадения в
названии объекта закупки: номер, процедура, этап, заказчик, опубликованная
НМЦК в рублях, дата окончания, официальные ссылки и SHA-256 HTML. Поле даты
не содержит точного времени/пояса, поэтому окно подачи остаётся `UNKNOWN`,
пока оно не проверено отдельно. `FAIL` возможен при уже прошедшей дате или
другом этапе. Охват явно `FIRST_PAGE_ONLY`; ноль совпадений не доказывает
отсутствия подходящих закупок на следующих страницах.

Для карточек 44-ФЗ `POST /v1/tender-discovery/eis-documents` читает страницу
документов и перечисляет опубликованные PDF/DOCX/XLSX/ZIP с URL и SHA-256
страницы. `POST /v1/tender-discovery/eis-attachment` скачивает выбранный файл
и показывает извлечённый текст; ZIP безопасно раскрывается существующим
extractor пакетов с перечислением файлов. Между запросами к ЕИС
соблюдается общий `Crawl-delay: 60` из robots.txt. Если ЕИС меняет разметку,
блокирует доступ или возвращает неполную страницу, результат имеет явный
статус ошибки, а не пустую успешную выдачу.

Для живого режима API нужен browser extra (`uv sync --extra browser`) и
установленный Chromium (`uv run --no-sync playwright install chromium`).
Общий cooldown хранится в `data/eis-public-browser`; для отдельного процесса
путь можно задать через `EIS_BROWSER_STATE_DIR`. Запросы чтения не сохраняют
карточки и документы в tenant-scoped базе: на этом этапе это preview.

Альтернативный вход — файл XML/ZIP, полученный оператором из ЕИС.
`POST /v1/tender-discovery/eis-export` читает только извещения с известными
корневыми элементами `epNotification*`/`fcsNotification*`, ограничивает вход,
распаковку и XML, отвергает DTD/ENTITY, выводит номер, название, доступные
поля НМЦК/срока и ссылки на вложения. Поиск учитывает простое совпадение русских
словоформ по началу слова; синонимы и смысловое соответствие ещё не определяются.
Ответ хранит SHA-256 исходного файла и каждого XML, имя элемента архива,
причины совпадения и число пропущенных XML. Несколько версий одного номера
показываются отдельно: код не объявляет версию актуальной без истории ЕИС.

`POST /v1/tender-discovery/eis-attachment` принимает только HTTPS URL с доменом
`zakupki.gov.ru` и путём `/epz/` либо официальным
`/44fz/filestore/public/1.0/download/`, не принимает другой конечный URL
скачивания и ограничивает обрабатываемый файл 20 МиБ. PDF/DOCX/XLSX/ZIP
передаются существующему нативному извлекателю. Ответ
содержит SHA-256 точных скачанных bytes, статус и причины извлечения, первые
4 000 символов текста. Файл не сохраняется в кейс автоматически; ссылка ЕИС
остаётся доступной для открытия и скачивания человеком.

На `/tender-discovery` показаны похожие закупки заказчиков, объяснения,
ссылки и документы. Эти карточки — только предварительные leads. Покрытие
для XML/ZIP ограничено файлом; подлинность загруженного файла — `UNKNOWN`, пока нет
прямой проверенной выдачи или подписи. НМЦК показывается только если число
корректно и валюта явно рублевая. Срок без UTC offset — `UNKNOWN`.
Истёкший срок или явная отмена — `FAIL`; будущий срок сам по себе не означает
открытую подачу. Экономика всегда `UNKNOWN` до полного ТЗ, подтверждённого
КП и всех расходов. Порядок результатов — релевантность слов названия,
затем срок; это не рейтинг прибыльности и не рекомендация `PARTICIPATE`.

## Граница и следующие необходимые срезы

1. Подключить зарегистрированный официальный сервис отдачи ЕИС по актуальной
   спецификации и разрешённому токену; подтвердить покрытие, watermark,
   версии/отмены и исторические изменения. Живой HTML-поиск сейчас покрывает
   только первую страницу и зависит от публичной разметки.
2. Прогнать несколько настоящих XML разных процедур 44-ФЗ/223-ФЗ, закрепить
   реальные версии схем и точные paths полей. Сейчас парсер поддерживает
   ограниченный совместимый набор тегов; невалидные элементы явно отклоняются.
3. Сохранять скачанные документы и их provenance tenant-scoped, собирать
   полный комплект, извлекать требования и передавать в существующие review
   и hard gates. Текстовая выдержка не доказывает полноту ТЗ.
4. Сопоставить запрос/профиль поставщика и варианты закупок по КТРУ/ОКПД2,
   географии, объёму, разрешениям и риску; затем получить КП и посчитать
   `base`, `realistic`, `conservative`. Только после этого сравнивать прибыль.

Официальный контекст: [Казначейство об ЕИС](https://roskazna.gov.ru/gis/eis-zakupki-gov-ru),
[публичный раздел документов ЕИС](https://zakupki.gov.ru/epz/main/public/document/view.html).
Доступность сервиса отдачи и его конкретная схема для этого окружения пока не
подтверждены; старые FTP-инструкции не считаются актуальным контрактом.

## Связанный пилот поиска и сравнения (S117)

`POST /v1/tender-discovery/runs` создаёт tenant-scoped сессию по товарному
запросу. Последующие `advance` выполняют не более одного сетевого шага:
страницу выдачи, подробную карточку, список документов или скачивание файла.
Пауза 60 секунд между обращениями к ЕИС соблюдается и после закрытия вкладки;
при новом открытии интерфейс продолжает сохранённую сессию. Пределы запроса:
1–20 страниц, 1–10 автоматически разбираемых кандидатов, 1–12 документов на
кандидата. По умолчанию — 3 страницы, 3 кандидата и 6 документов. Выдача ЕИС
может меняться во время обхода, поэтому даже завершённая сессия имеет
`PARTIAL`, если полный охват и история версий не подтверждены.

Пилот хранит исходные HTML и скачанные файлы в локальной tenant-scoped SQLite
(`data/eis-discovery.sqlite3`, до 100 МиБ исходников на сессию), вместе с
SHA-256, ссылками и локаторами. Документы разбираются нативным извлекателем;
формулировки требований показаны только как кандидаты с provenance. Роль
документа и полнота комплекта остаются `UNKNOWN` до проверки человеком.
Сбои и неподдержанные форматы видимы отдельно от успешного пустого поиска.

Для сравнения оператор вводит стоимость товара на весь лот, прочие расходы,
ставку НДС, источник цены и сценарные допущения. Сервер через `Decimal`
рассчитывает `base`, `realistic`, `conservative`; порядок оценённых закупок
определяется консервативной прибылью. Это предварительная гипотеза по НМЦК,
а не обещание дохода или рекомендация `PARTICIPATE`. Без подтверждённых
расходов результат `UNKNOWN`; истёкшая или отменённая закупка блокируется.
Автоматический поиск действительного КП и анализ ставок конкурентов в этом
срезе не реализованы.

## История заказчика по выбранной закупке 44-ФЗ (S118)

Кнопка «Посмотреть контракты заказчика» запускает отдельный ограниченный
workflow. Из сохранённой подробной карточки закупки берётся только точная
ссылка `Заказчик` на официальную карточку организации; если она не найдена или
неоднозначна, связь остаётся `UNKNOWN`. Карточка организации даёт явно
подписанный ИНН и собственную ссылку на реестр её контрактов. Пилот меняет
наблюдённый фильтр `contractStageList=0` на `1` («Исполнение завершено») и
читает **только первую страницу**, не более 10 карточек. Каждая показанная
карточка должна иметь официальный реестровый URL, статус «Исполнение завершено»
и того же заказчика. Сохраняются исходные HTML, SHA-256, локаторы, время чтения
и tenant-scoped audit.

Интерфейс показывает номер, предмет, явно подписанную цену контракта и дату
заключения. Отсутствующие поля остаются `UNKNOWN`; другие стадии и заказчики
не включаются. Эти контракты не меняют предварительную экономику и не создают
рейтинг заказчика: выбранная страница не доказывает полноту истории, оплату,
приёмку или размер скидки относительно НМЦК. Анализ актов и связи с исходным
извещением — отдельные следующие шаги.

Для локального теста без PostgreSQL: установить browser extra и Chromium,
собрать web (`npm install`, `npm run build`) и запустить
`uv run --no-sync python scripts/start-eis-pilot.py`. Скрипт создаёт локальный
токен без вывода в консоль и поднимает API и UI только на `127.0.0.1`:
<http://127.0.0.1:3000/tender-discovery>. Он не использует основной API кейсов.

## Поиск истории заказчика по товару (S119)

Для выбранной закупки 44-ФЗ кнопка «Найти контракты заказчика по товару»
повторно использует проверенную ссылку из карточки организации, оставляет
фильтр «Исполнение завершено» и добавляет товарный запрос поставщика в
`searchString`. Слова намерения («хочу», «перепродавать» и подобные) убираются;
пустой или слишком длинный запрос отклоняется. После ответа проверяются
значения поисковой строки, стадии и ИНН заказчика в форме ЕИС. Если форма не
подтверждает фильтры, результат помечается `SOURCE_CHANGED`, а не пустой
успешной выдачей.

Для каждой карточки сохраняются точный URL и номер контракта, SHA-256
исходного HTML, локатор, время чтения и, если ссылка однозначна, URL и номер
связанного извещения ЕИС. `MATCHED_VISIBLE` означает совпадение слов запроса
с видимым полем «Объекты закупки»; иначе остаётся `UNKNOWN`, поскольку ЕИС
может искать и по другим полям. Интерфейс показывает сначала подтверждённые
совпадения и объясняет основание для каждой карточки. Явное сообщение ЕИС
«Поиск не дал результатов» при подтверждённых фильтрах даёт ноль результатов
**только для текущей выдачи**. Отсутствие карточек без этого сообщения —
ошибка разметки.

Поиск ограничен первой страницей (до 10 карточек). Он не доказывает полноту
истории, связь цены контракта с НМЦК, скидку на аукционе или доходность для
поставщика. Цены исторических контрактов не подмешиваются в расчёт
`base`/`realistic`/`conservative`; для решения нужны действительное КП и
проверенный состав текущего лота.

Дальнейший путь к поиску по подтверждённому публичному корпусу ЕИС,
сравнению документов, проверенной экономике и конкуренции описан в
[плане S120–S127](26-eis-full-corpus-plan.md). Пилот S116–S119 не является
подтверждением полного охвата.

## Проверка точного номера из живой выдачи (S128)

Публичный поиск по товарному запросу возвращает только первую страницу
кандидатов. Для номера 44-ФЗ кнопка «Проверить XML и поставить документы в
очередь» вызывает `POST /v1/tender-discovery/eis-live/{purchase_number}/verify`.
Сервер с операторской ролью обращается к официальному машинному сервису
`getDocsIP/getDocsByReestrNumberRequest` с зарегистрированным токеном,
проверяет связанный `getPreparedPart` и полный набор архивов, сверяет номер
каждого XML с запрошенным, затем атомарно сохраняет ZIP, версии XML и
provenance в tenant-scoped индексе. Документы привязываются к точным номеру,
версии и SHA-256 XML; фоновая очередь скачивает и разбирает их отдельно.

`NO_DATA`, `PREPARING`, `SERVICE_ERROR`, ошибка транспорта и конфликт
источника показываются явно. Даже успешный ответ означает только проверку
одного номера (`ONE_NUMBER_ONLY`); отсутствие карточки в первой странице
поиска не доказывает её отсутствия в ЕИС. У 223-ФЗ этот путь машинного
сервиса пока не подключён. Полнота выдачи, комплекта документов, требования,
цены поставщика и выгода остаются `UNKNOWN`, пока нет отдельного evidence.

### Проверяемая пагинация и счётчики (S133, 01.10.2026)

Текущий размер страницы — 100. `DiscoveryRequest.search_page_size` допускает
100 или 50; резерв 50 выбирается при **новой** сессии. Размер не меняется
посреди обхода, чтобы не сдвинуть offset и не пропустить карточки. `_200`
убран из production после обнаружения повторов в S131. Предел программы
по-прежнему 20 страниц; отсутствие ссылки продолжения — лишь source hint.

Парсер сохраняет номер каждой идентифицируемой строки до проверки названия
и товарного совпадения. Поэтому карточка без названия может входить в
проверку уникальности, но не в shortlist. Номер должен согласовываться с
официальной ссылкой. Непроверяемые строки учитываются отдельно.

Persisted `search_pages` содержит номер/размер страницы, URL, aware время,
SHA-256 исходного HTML, raw номера, счётчики и fingerprint отсортированного
множества номеров. Fingerprint не зависит от HTML/порядка/совпадений в названии.
Повтор ранее прочитанного набора → `REPEATED_PAGE`; страница с другим набором,
но без новых номеров → `NO_NEW_IDENTIFIERS`. Следующая страница не запрашивается,
а анализ уже полученных кандидатов продолжается. Решение остановки сохраняется
в tenant-scoped audit, вместе с evidence страницы.

Счётчики в API/UI:

- `scanned_count` — все прочитанные строки, включая повторы;
- `identified_count` — различные проверенные номера в сохранённых страницах;
- `unique_scanned_count` — точное число различных закупок **только среди
  прочитанных страниц**, либо null/UNKNOWN при неполных номерах/evidence;
- `duplicate_count` — подтверждённые повторные вхождения номеров;
- `unparsed_count` — строки, из которых не получена проверяемая карточка.

При неполной идентификации обход останавливается с `IDENTIFIERS_INCOMPLETE`,
не объявляет исчерпание выдачи. Старые сессии без page evidence совместимы
при загрузке, но не продолжают прежний offset (`LEGACY_STATE_UNVERIFIED`);
уникальный охват UNKNOWN. API хранит SQLite сессий/артефактов/audit в постоянном
томе VPS. Общий 60-секундный cooldown сохранён. Завершённый workflow остаётся
PARTIAL: проверка уникальности страниц не доказывает полный охват ЕИС,
пригодность всех карточек, полноту документов или прибыль.
